# スキルを優れたものにする書き方

スキルは、確率的なシステムから決定性を引き出すために存在します。**予測可能性**――毎回同じ出力を生成することではなく、エージェントが毎回同じ *プロセス* をたどること――が根本的な美徳であり、以下のすべての仕組みはそのためにあります。

**太字の用語** は `GLOSSARY.md` で定義されています。完全な意味についてはそちらを参照してください。

## 呼び出し

コストの異なる 2 つの選択肢があります。

- **model-invoked** スキルは **description** を持つため、エージェントが自律的に起動でき、さらに他のスキルからも利用できます（もちろん名前を入力して呼び出すことも可能です）。ただし **context load** に影響します。説明文は毎ターンのコンテキストに含まれるからです。仕組みとしては、`disable-model-invocation` を省略し、モデル向けの説明文を豊富なトリガーフレーズ付きで記述します（「ユーザーが〜したい場合に使用」「〜に言及した場合に使用」など）。
- **user-invoked** スキルは説明文をエージェントの利用範囲から除外します。呼び出せるのはskill名を入力したユーザーだけであり、他のスキルからも利用できません。コンテキスト負荷はゼロですが、代わりに **cognitive load** を消費します。つまり、スキルの存在を覚えておくインデックスは *あなた自身* になります。仕組みとしては、`disable-model-invocation: true` を設定します。`description` は人間向けになり、トリガー一覧は除去された 1 行要約になります。

モデル起動を選ぶのは、エージェント自身がそのスキルを利用する必要がある場合、または他のスキルが利用する必要がある場合だけにしてください。手動でしか起動しないのであれば、ユーザー起動にしてコンテキスト負荷を発生させない方がよいでしょう。

ユーザー起動スキルが増えすぎて覚えきれなくなった場合、その蓄積した認知負荷は **router skill** によって解決できます。これは、他のスキルとその利用タイミングを案内する 1 つのユーザー起動スキルです。

## 説明文を書く

モデル起動型の **description** には 2 つの役割があります。スキルの内容を説明すること、そして起動すべき **branch** を列挙することです。1 語増えるごとに **context load** が増えるため、説明文は本文以上に厳しく削られる必要があります。

- **先頭にスキルの leading word を置く。** 説明文は起動のために存在します。
- **1 branch に 1 trigger。** 同じ branch を言い換えるだけの同義語は **duplication** です。たとえば「TDD を用いて機能を実装する」と「テストファースト開発を求めている」は同じ branch を二度書いています。本当に異なる branch だけを残してください。
- **本文に既にあるアイデンティティ情報を削除する。** 説明文はトリガーと、「他のスキルが必要とした場合」の利用条件だけにとどめます。

## 情報階層

スキルは **steps** と **reference** という 2 種類の内容から構成されます。スキルは steps のみ、reference のみ、あるいは両方を含むことができます。重要なのはどちらを使うか、そしてそれを **information hierarchy** のどこに配置するかです。

1. **In-skill step** — `SKILL.md` に記載された順序付きのアクション。最も重要な階層です。エージェントが何をどの順序で行うかを定義します。各 step は **completion criterion**（完了条件）で終わります。これは作業完了を判断する条件です。*検証可能* であること（完了か未完了かを判別できるか）、そして必要な場合は *網羅的* であること（「変更されたすべてのモデルを確認した」など）を重視してください。曖昧な条件は **premature completion** を招きます。
2. **In-skill reference** — `SKILL.md` 内の定義、ルール、事実です。必要時に参照されます。同列に並んだルール群であることもしばしばあり、それは問題ではありません。*このスキルは完全に reference です。*
3. **External reference** — `SKILL.md` の外へ出された reference です。**context pointer** によって参照され、必要になったときだけ読み込まれます。（`GLOSSARY.md` のような関連ファイルから、スキル外に存在する完全な **external reference** までを含みます。）

厳格な完了条件は徹底した **legwork**（調査・掘り下げ作業）を促します。これは step 型でも reference 型でも同じです。

下に追い出しすぎると重要情報が隠れ、残しすぎると上位が肥大化します。この緊張関係こそが設計上の判断です。

**Progressive disclosure** とは、情報を階層の下へ移動し、関連ファイルへ分離することです。上位を読みやすく保つための手法です。スキルによっては複数の利用形態を持ち、そのそれぞれが **branch** です。分岐は情報を分離する際の判断基準として有効です。すべての branch が必要とするものは本文に残し、一部のみが利用する情報は context pointer の先へ移動します。**context pointer** では参照先ではなく *文言* が、いつどの程度確実に情報へ到達するかを決定します。

情報階層が「どこに置くか」を決める一方、**co-location** は「何を隣に置くか」を決めます。定義、ルール、注意事項などは分散させず、同じ見出しの下にまとめてください。

## 分割するタイミング

**Granularity** はスキルをどれだけ細かく分割するかです。分割には必ずコストが発生するため、その価値がある場合のみ行います。

- **By invocation** — 独立した **leading word** があり、単独で起動されるべき場合、または他のスキルが利用する必要がある場合に **model-invoked** スキルとして分割します。そのためには新たな **description** による **context load** を支払う価値が必要です。
- **By sequence** — 後続の **steps**（ある step の **post-completion steps**）が前の step を急いで終わらせる誘惑となる場合、steps を分割します。見えなくすることで現在の作業に対する **legwork** を促進します。

## 剪定

すべての意味は **single source of truth** に置いてください。振る舞いを変更する際に、1 か所だけ編集すれば済む状態です。

各行に対して **relevance** を確認してください。その行は本当にスキルの役割に関係していますか。

次に **no-op** を探してください。行単位ではなく文単位で確認します。no-op テストに失敗した文は、単語を削るのではなく文全体を削除してください。積極的に削除してください。

## Leading words

**Leading word** とは、モデルの事前学習に既に存在するコンパクトな概念であり、スキル実行中の思考の軸になるものです（例: *lesson*、*fog of war*、*tracer bullets*）。本文全体で繰り返し利用されることで分散的な定義が形成され、少ないトークンで大きな振る舞い領域を支えます。

これは予測可能性に対して二重の役割を果たします。本文では *実行* を固定し、説明文では *起動* を固定します。同じ言葉がプロンプト、ドキュメント、コードに存在すると、モデルはその言葉とスキルを結び付け、より確実に起動します。

スキルを leading word によってリファクタリングできる箇所を探してください。複数箇所で説明されている概念（**duplication**）や、1 つのアイデアを説明するために長い文を使っている箇所は、1 つのトークンへ **collapse** できる可能性があります。

例:

- 「高速で、決定的で、オーバーヘッドが低い」 → *tight* — 1 つの事前学習済み単語へ集約する（*tight* なループ）。
- 「信頼できるループ」 → *red* — 曖昧な状態を二値判定へ変換する（そのループがバグで *red* になるか、ならないか）。

利点は 2 つです。トークン数が減ること、そしてエージェントの思考を固定する強力なフックになることです。あらゆるスキルには leading word に置き換えられる重複表現が存在すると考え、それを探してください。

## 失敗パターン

これらは、ユーザーがスキル利用時に抱えている問題を診断するために使います。

- **Premature completion** — 本当に完了する前に step を終えてしまうこと。まず完了条件を改善してください。それでも曖昧で急ぎが発生する場合のみ、後続 step を分離してください。
- **Duplication** — 同じ意味が複数箇所に存在すること。保守コスト、トークン数、重要度の誤った増加を招きます。
- **Sediment** — 追加は安全、削除は危険と感じることで積み重なった古い層です。剪定を行わないスキルの典型的な末路です。
- **Sprawl** — すべての行が必要であっても長すぎるスキルです。可読性と保守性を損ない、トークンを浪費します。対策は情報階層です。**reference** を pointer の先へ移し、**branch** や sequence ごとに分割します。
- **No-op** — モデルが既定で従うため、書いても意味のない記述です。テストは「既定動作と比較して振る舞いが変わるか」です。弱い leading word（*be thorough* など）は no-op になりがちです。対策はより強い word（*relentless* など）です。
- **Negation** — 禁止による誘導は逆効果です。*don't think of an elephant* は象を思い出させます。禁止する代わりに **positive** な振る舞いを記述してください。本当に必要な禁止事項だけを残し、その場合も代替行動を明記してください。
