# Triage（トリアージ）

プロジェクトの課題トラッカー上の課題を、小さなトリアージ状態機械に従って進めます。

このリポジトリが外部プルリクエストをリクエストインターフェースとして扱う場合（issue-tracker設定を参照）、トリアージはそれらも対象です：**PRはコードが付属した課題である** — 同じ役割、同じ状態、同じ機械で扱います（以下に「for a PR」として差分あり）。`#42` のような参照は、トラッカー設定に基づいて課題またはPRに解決してください。

トリアージ中に課題トラッカーへ投稿するすべてのコメントや課題は、必ず以下のディスクレーマーで開始してください：

```
> *This was generated by AI during triage.*
```

- [AGENT-BRIEF.md](AGENT-BRIEF.md) — エージェントブリーフの書き方
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) — `.out-of-scope/` ナレッジベースの仕組み

## Roles（役割）

2つの**カテゴリロール**：

- `bug` — 何かが壊れている
- `enhancement` — 新機能または改善

5つの**状態ロール**：

- `needs-triage` — メンテナの評価が必要
- `needs-info` — 追加情報待ち
- `ready-for-agent` — 十分に定義されておりエージェント実装可能
- `ready-for-human` — 人間による実装が必要
- `wontfix` — 対応しない

PRの場合も同様にコードに対して解釈します：`ready-for-agent` はブリーフ完備でエージェントが次作業へ、`ready-for-human` は人間がマージ可能。

すべての課題はカテゴリ1つ＋状態1つを持ちます。状態が競合する場合はメンテナへ確認してください。

これらは正規のロール名です — 実際のラベルとは異なる場合があります。マッピングは提供されているはずです。提供されていない場合は、ユーザーに `/setup-matt-pocock-skills` を実行するよう伝えてください。

状態遷移：未ラベルは通常 `needs-triage` へ。そこから `needs-info`、`ready-for-agent`、`ready-for-human`、`wontfix` へ移行します。`needs-info` は回答後 `needs-triage` へ戻ります。メンテナはいつでも上書き可能です。

## Invocation（呼び出し）

メンテナは `/triage` を自然言語で実行内容指定します。例：

- 「対応が必要なものを見せて」
- 「#42 を見よう」
- 「#42 を ready-for-agent に」
- 「エージェントが対応可能なものは？」

## Show what needs attention（注意すべき点）

課題トラッカーを確認し、以下3分類で提示（古い順）：

1. **Unlabeled** — 未トリアージ
2. **`needs-triage`** — 評価中
3. **`needs-info`（返信あり）** — 再評価が必要

PR が対象範囲に含まれる場合、外部 PR もこれらの分類に入れ、各行に`[PR]` / `[issue]`のタグを付けること。「Discovery（発見フェーズ）」では 外部 PR のみを対象とする（誰を外部とみなすかはトラッカー設定で決まる）。共同作業者（コラボレーター）が作成中の PR はトリアージ対象ではない。このフィルターは Discovery のみで使われるものであり、明示的に指定された PR は、作者に関係なく必ずトリアージされる。

件数と各項目の 1 行サマリーを表示し、メンテナーが選べるようにする。

## Triage a specific issue or PR（特定の問題点/PRのトリアージ）

1. **Gather context.** 課題またはPRの全文（本文、コメント、ラベル、作成者、日付；PRの場合は差分も含む）を読みます。既存のトリアージノートを解析し、解決済みの質問を再度聞かないようにします。プロジェクトのドメイン用語を使ってコードベースを探索し、対象領域のADRを尊重します。コードベースに対して次の2つのチェックを実行します：
   
   (a) **redundancy（重複）** — リクエストされた振る舞いがすでに実装されていないかを、文言ではなくドメイン概念で検索し、どこを探したかを報告します。見つかった場合、それは既に実装済みのため `wontfix`（手順5）とします。
   
   (b) **prior rejection（過去の却下）** — `.out-of-scope/*.md` を確認し、このリクエストに類似するものを提示します。

2. **Recommend.** カテゴリと状態の推奨、およびその理由をメンテナに伝えます。また、このリクエストに関連するコードベースの簡潔なサマリー（既に実装されているかどうかを含む）を添えます。指示を待ちます。

3. **Verify the claim.** グリル（質問）に入る前に、主張が正しいかを確認します。バグの場合は報告者の手順に従って再現を試みます。PRの場合は差分が主張どおりに機能するか確認します — チェックアウトし、関連するテストやコマンドを実行します。結果を報告します：再現・確認成功（コードパスを含む）、失敗、または情報不足（`needs-info` の強いシグナル）。検証が確認できていると、より強力なエージェントブリーフになります。

4. **Grill (if needed).** リクエストの詳細化が必要な場合は、Skill tool を "grilling" と "domain-modeling" で 2 回呼び出し、1 ラウンド分の質問ずつ尋ねながら形を整えます。ドメイン用語を明確にし、意思決定が確定するたびに `GLOSSARY.md` / ADR を更新します。

5. **Apply the outcome:**
   - `ready-for-agent` — エージェントブリーフをコメントとして投稿（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human` — エージェントブリーフと同様の構造だが、委譲できない理由（判断が必要、外部アクセス、設計判断、手動テストなど）を明記。
   - `needs-info` — トリアージノートを投稿（以下テンプレート）。
   - `wontfix` — クローズし、理由に応じたコメントを付ける：
     - **Already implemented** — 変更は既にコードベースに存在。場所を示す。`.out-of-scope/` には書かない（そこは「却下」用）。
     - **Rejected (bug)** — 丁寧に説明してクローズ。
     - **Rejected (enhancement)** — `.out-of-scope/` に記録し、リンクを貼ってクローズ（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage` — 状態ロールを付与。必要に応じてコメント。

## Quick state override（迅速な状態上書き）

メンテナが「#42 を ready-for-agent に移動」と指示した場合、その指示を信頼してロールを直接適用します。実施内容（ロール変更、コメント、クローズ）を確認してから実行してください。グリルはスキップします。`ready-for-agent` に移行する際に、グリルセッションを行っていない場合は、エージェントブリーフを書くかどうかを確認してください。

## Needs-info template（情報不足時のテンプレート）

```markdown

## Triage Notes（トリアージノート）

**これまでに判明していること:**

- point 1
- point 2

**あなた（@reporter）からまだ必要な情報:**

- question 1
- question 2
```

グリル中に解決した内容はすべて「established so far」に記録し、作業内容が失われないようにします。質問は具体的かつ実行可能なものである必要があり、「詳細を提供してください」のような曖昧なものは避けてください。

## Resuming a previous session（前回セッションの再開）

課題またはPRに過去のトリアージノートが存在する場合はそれを読み、報告者が未解決の質問に回答しているかを確認し、更新された状況を提示してから作業を続けます。解決済みの質問は再度尋ねないでください。
