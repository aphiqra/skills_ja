# Prototype

プロトタイプとは **問いに答えるための使い捨てコード** です。問いがその形を決めます。

## Pick a branch

どの問いに答えるのかを特定します — ユーザーのプロンプト、周囲のコード、またはユーザーに確認して判断します：

- **「このロジック / 状態モデルは妥当か？」** → [LOGIC.md](LOGIC.md)。紙では考えにくいケースで状態機械を動かす、小さな対話型ターミナルアプリを構築します。
- **「これはどのように見えるべきか？」** → [UI.md](UI.md)。単一ルート上に大きく異なる複数のUIバリエーションを生成し、URLの検索パラメータとフローティングのボトムバーで切り替え可能にします。

この2つは全く異なる成果物を生みます — 誤るとプロトタイプ全体が無駄になります。問いが本当に曖昧でユーザーに確認できない場合は、周囲のコードにより適した方（バックエンドモジュールならロジック、ページやコンポーネントならUI）を選び、その前提をプロトタイプの冒頭に明記します。

## Rules that apply to both

1. **最初から使い捨てであることを明確にする。** プロトタイプコードは実際に使用される場所（対象となるモジュールやページの近く）に配置し、文脈が明確になるようにする。ただし、名称によって誰が見てもプロトタイプであり本番コードではないと分かるようにする。UIルートのプロトタイプの場合は、既存のルーティング規約に従い、新しいトップレベル構造を作成しない。
2. **1コマンドで実行可能にする。** プロジェクトの既存のタスクランナーがサポートしている方法（`pnpm <name>`、`python <path>`、`bun <path>` など）を使用する。ユーザーが考えずに起動できることが必須。
3. **デフォルトで永続化しない。** 状態はメモリ上に保持する。永続化はプロトタイプが「検証する対象」であり、依存すべきものではない。データベースが明示的に関与する場合は、スクラッチDBまたは「PROTOTYPE — wipe me」と明示されたローカルファイルを使用する。
4. **仕上げは行わない。** テスト、最小限を超えるエラーハンドリング、抽象化は不要。目的は素早く学習すること。
5. **状態を可視化する。** 各アクション（ロジック）または各バリアント切替（UI）のたびに、関連する状態全体を表示・レンダリングして、何が変化したかをユーザーが確認できるようにする。
6. **完了時に成果を記録する。** 検証された意思決定は本体コードに取り込み、その後プロトタイプ自体を**一次情報源**として保存する：メインとは別の使い捨てブランチにコミットし、実装課題からそのブランチへのコンテキストポインタを残す。また、結論（どの問いを解決したか、どの判断に至ったか）も課題やコミットに記録する。本流ブランチには検証済みの決定のみを残す。
