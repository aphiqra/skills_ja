# Ask Matt

あなたはすべてのスキルを覚えているわけではないので、尋ねてください。

スキルが何をするかを述べたり、あるステップを飛ばすよう勧めたりする前に、そのスキルの SKILL.md を読んでください。ここにある要約は全体像をつかむためだけのものです。

**フロー**とはスキルを通る経路です。ほとんどの経路は1つの**メインフロー**に沿って進み、2つの**オンランプ**がそこに合流します。それ以外はスタンドアロン、または下層で動く語彙レイヤーです。

## メインフロー: アイデア → 実装

ほとんどの作業が通るルートです。アイデアがあり、それを構築したい場合。

1. **`/grill-with-docs`** はインタビューによってアイデアを磨きます。**作業ディレクトリで作業している場合**は常にここから開始します: これは状態を保持し、`GLOSSARY.md` や ADR に学習内容を保存します。(作業ディレクトリがない場合は代わりに `/grill-me` を使用します。スタンドアロンを参照。どちらも同じ `/grilling` プリミティブを実行しますが、`grill-with-docs` は記録を残すので、記録を残せるリポジトリがあるなら常にこちらのほうが優れています。)

2. **Branch: すべての質問を会話で解決できますか？** 実行可能な答え（状態、ビジネスロジック、実際に見る必要のあるUI）が必要な場合、プロトタイプに迂回し、両方向で **`/handoff`** によって接続します（プロトタイプは独自のディレクトリに置かれるので、まさに `/handoff` の出番です。フェーズの境界を参照）:
   - **`/handoff`** で外部へ、その後そのファイルで新しいセッションを開始し、
   - **`/prototype`** で使い捨てコードで質問に答え、
   - 学んだことを **`/handoff`** で戻し、元のアイデアスレッドから参照します。

3. **Branch: これは複数セッションにまたがるビルドですか？**
   - **はい** → **`/to-spec`**（スレッドを仕様に変換）し、その後 **`/to-tickets`** でトレーサーバレットチケットに分割し、それぞれが**ブロッキングエッジ**を宣言します。その後、次の2つのどちらかの方法でチケットを進めます:
     - チケットごとに **`/implement`** を実行し、**各チケットの間で `/clear` してコンテキストをクリア**します。ローカルトラッカーでは `.scratch/<feature>/issues/` に1チケット1ファイルとして管理し、ブロッカー優先で手動処理します。実際のトラッカーではエッジがネイティブな依存関係リンクになるので、ブロッカーが完了したチケットはどれでも取得できます。各チケットは自己完結しているので、前のチケットのコンテキストは捨ててかまいません。
     - 仕様全体を1回で実行する **`/implement-spec`**。チケットを**タスクグラフ**として読み、着手可能な**フロンティア**全体で実装担当のサブエージェントを並列に走らせ、すべてを1つの**統合ブランチ**に載せます。各チケットを自分で進めるより、ビルド全体を指揮したい場合に使います。
   - **いいえ** → 同じコンテキストウィンドウ内でそのまま **`/implement`**。

   いずれの場合も、コードは **`/tdd`** を駆動して（レッド→グリーンを1スライスずつ）構築され、**`/code-review`**（標準 + 仕様の2軸による差分レビュー）で締めくくられます。`/implement` はチケットごとに両方を実行します。`/implement-spec` では各実装担当が `/tdd` を駆動し、統合ブランチ全体に対して `/code-review` を1回実行します。仕様なしで具体的な振る舞いをテスト駆動で構築したい場合は単独で **`/tdd`** を使用し、固定された基準に対してブランチやPRをレビューしたい場合は単独で **`/code-review`** を使用します。

   作業をプルリクエストとして出すときは、**`/pr`** が本文の形を整えます: 変更を示す最小限のビジュアル、動作することを示す変更前後の証拠、そして一方通行か両方向のドアかの判断です。モデル起動型なので、エージェントは PR を書くたびにこれを使います。

4. **`/retro`** がループを閉じます。ビルドの後、特にうまくいかなかったビルドの後に、セッションを振り返り、コードではなくエージェントの**環境**への変更を提案します: ナビゲーションの手がかり、自動チェック、`/code-review` が適用するコーディング規約、ステアリングファイル、ツールです。機械的なミスは決定的なチェックに、判断を要するものはコーディング規約になります。次のビルドは、より良い環境から始まります。

### コンテキスト管理

ステップ1〜3は**途切れのない単一コンテキスト**で維持します（`/to-tickets` の後まで圧縮やクリアをしないでください）。そうすることでインタビュー、仕様、チケットが同じ思考を基に構築されます。その後の各 `/implement` はチケットを基に新しく開始します。`/retro` は振り返る対象のセッション内で、クリアする前に実行します。クリアした後なら、代わりにそのセッションのログを指定してください。

この制限は [**スマートゾーン**](https://www.aihero.dev/ai-coding-dictionary/smart-zone) によります: モデルが鋭く推論できるウィンドウ（最先端モデルで約15万トークン）です。`/to-tickets` の前にこれに近づいた場合、品質低下のまま続けずに、最も近いフェーズの境界で `/compact` して続行してください（フェーズの境界を参照）。

## オンランプ

作業を生み出し、メインフローに合流する開始状況。

- **バグや依頼が積み上がっている** → **`/triage`**。問題をトリアージの役割に沿って整理し、エージェント対応可能な課題を生成します。後で **`/implement`** がそれらを処理します。

  トリアージは**自分が作成していない**課題のみに使用します: バグ報告、届いた機能リクエストなど、未整理のまま届いたものすべてです。`/to-tickets` で作成されたチケットはすでにエージェント対応可能なので、**トリアージしないでください**。

- **何かが壊れている** → **`/diagnosing-bugs`**。難しいバグ向け: 一見して分からないもの、断続的な不具合、既知の正常状態の間で入り込んだ回帰。**厳密なフィードバックループ**（*このバグ*で確実に失敗する単一コマンド）が確立されるまでは仮説を立てず、その後回帰テストとともに修正します。修正が入ったら、同じセッションで **`/retro`** を実行し、何がこのバグを防げたかを尋ねます。バグを固定する良い境界がないことが本当の発見なら、それは **`/improve-codebase-architecture`** の仕事です。

- **巨大で見通しの悪い取り組み: 新規プロジェクトや非常に大きな機能開発など、1セッションでは収まらないもの** → **`/wayfinder`**。ここで最も認知負荷が高いフローです。目的地までの道筋が見えないとき、課題トラッカー上に**意思決定チケット**の**共有マップ**を作成し、1つずつ解決します。成果物ではなく**意思決定**を生み出しながら、霧が晴れて道が明確になるまで続けます。**`/grill-with-docs`** が1セッションで扱えるアイデアを磨くのに対し、wayfinder は扱えない規模のアイデアに使います。またより遅く重いので、まさにその用途に限定し、範囲の明確な機能には決して使わないでください。

  マップが明確になったら**構築せずに引き渡します**: メインフローの **`/to-spec`** に合流し、マップのリンクされた決定を構築可能な計画に統合し、その後 `/to-tickets` と `/implement` を通常どおり実行します。マップから直接 `/implement` に進むとその統合を飛ばし、リンクされた詳細が失われるので、実際に小規模だったと分かった場合のみ直接 `/implement` に進みます。

## コードベースの健全性

機能開発ではなく、ただの保守です。

- **`/improve-codebase-architecture`** は、エージェントが扱いやすいコードベースを維持するため、時間があればいつでも実行します。**深いモジュール化の機会**を表面化し、1つ選ぶと _アイデアが生成され_、メインフローの `/grill-with-docs` に持ち込めます。候補を見つける調査であり、選んだ候補の設計は下記の **`/codebase-design`** で行います。

## 下層の語彙

他のスキルの*下で*動作する2つのモデル起動型リファレンス。それぞれが自分の語彙の単一の情報源です。プロセスではなく**言葉**が問題のときに直接使用するか、上位スキルから呼び出されます。

- **`/domain-modeling`**: プロジェクトの*ドメイン*言語を明確化します: 曖昧な用語に異議を唱え、過負荷な単語を解決し（例: 「アカウント」が3つの役割を担っている）、元に戻しにくい決定をADRとして記録します。`/grill-with-docs` が `GLOSSARY.md` を整理された用語集として維持するために駆動する、能動的な規律です。
- **`/codebase-design`** は、モジュールの*形*を設計するための深いモジュールの語彙（module、interface、depth、seam、adapter、leverage、locality）です: 明確な境界にある小さなインターフェースの背後に多くの振る舞いを持たせます。`/tdd` と `/improve-codebase-architecture` はどちらもこの語彙を使います。

## フェーズの境界

**フェーズ**とは、セッション内の作業のまとまりです: インタビュー、実装、QA など。2つのフェーズの**境界**では5つの選択肢があり、そのどれを選ぶかが、このマップ全体で最も曖昧な判断です:

- **Continue**: そのまま続けます。コストはかからず、何も失いません。
- **`/clear`**: ウィンドウを空にします。ここにあるものが次の作業に何も関係ないときに使います。
- **`/handoff`** は持ち運べる Markdown ファイルを書き出します。用途は狭く、**新しいハーネス**、**新しいディレクトリ**、**同僚**への引き継ぎ、または**フェーズの途中**でサイドタスクを分岐させるときだけです。得られるのは持ち運びやすさです。
- **サブエージェント**: 範囲を絞ったタスクを専用のウィンドウに送り、レポートを受け取ります。
- **`/compact`** はこのコンテキストを圧縮し、それを元に新しいセッションを始めます。これが**デフォルト**ですが、最初に手を伸ばすものではなく、判断ツリーの一番下にあります。

順序付きの判断ツリーについては [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) を読んでください: 5つの質問、各分岐の理由、そして一次情報のコストがあるために **Continue** を最初に除外すべき理由が書かれています。判断は境界**で**行います。フェーズの途中では、そのまま続けるか、残りをサブエージェントに分割してください。

## スタンドアロン

メインフローの完全に外側。

- **`/grill-me`**: `/grill-with-docs` と同じ徹底的なインタビューですが、**ステートレス**です: ローカルには何も保存せず、`GLOSSARY.md` も作りません。**作業ディレクトリで作業していない**とき（計画、設計、文章など、リポジトリに紐づかないものを磨くとき）に使います。作業ディレクトリにいるなら、代わりに `/grill-with-docs` を使ってください: 同じインタビューを行い、記録も残すので、明らかにそちらのほうが優れています。
- **`/grilling`** はインタビューのプリミティブそのものです: ラウンド、フロンティア、事実はエージェントの仕事で、決定はあなたのもの、という仕組みです。`/grill-me` と `/grill-with-docs` はその2つの名前付きの入口であり、`/triage`、`/wayfinder`、`/improve-codebase-architecture` はすべて内部でこれを実行します。何のラッパーもないインタビューだけが欲しいときにだけ、直接使ってください。
- **`/prototype`** は、設計上の1つの疑問に答えるための小さく使い捨てのプログラムです: 状態モデルが適切か、UIはどう見えるべきか。使い捨てとはコードの書き方に対する制約であって、破棄する約束ではありません: 答えは本番のコードに取り込み、プロトタイプ自体は main から外れた `prototype/<name>` ブランチに**一次情報**として残し、実装の課題からそこを指します。メインフローのステップ2の迂回路ですが、紙上で決めにくい設計問題にいつでも使用できます。
- **`/research`**: 読み込み作業を**バックグラウンドエージェント**に委任します: **一次情報**を基に疑問を調査し、引用付きの Markdown ファイルをリポジトリに残します。読み込み中も作業を続けられます。生成されたファイルはメインフローの `/grill-with-docs` に*持ち込む*ものです。調査は思考の材料であって、思考の代わりではありません。
- **`/to-questionnaire`** は、あなたを止めているものが、あなたの頭の中やコードベースではなく**別の誰かの頭の中**にあるときに使い、その人が記入するアンケートを書きます。`/grill-me` の逆です: 主題についてあなたにインタビューするのではなく、**送る**ことについて（誰に送るのか、何を返してほしいのか）インタビューし、その隙間に質問を向けます。返ってきたものは `/grill-with-docs` や `/to-spec` の材料になります。
- **`/wizard`** は、**人間**にしかできない手順のためのものです: インフラのプロビジョニング、認証情報や CI シークレットの設定、慣れないサードパーティのダッシュボードの操作、一度きりのマイグレーションや切り替えの実行などです。各 URL を開き、各値を受け取り、`.env` と GitHub シークレットに書き込む対話型の bash スクリプトを生成するので、その手順を毎回エージェントに説明し直す必要がなくなります。モデル起動型なので、エージェントはあなたにしか越えられない壁に突き当たった瞬間にこれを使います。エージェント自身でできることなら、エージェントがやるべきです。これは本当に人間が関わる必要がある場面のためのものです。
- **`/wait-what`** は、メッセージが腑に落ちなかったときの修正手段です。会話の途中で、他のどのスキルの中でも使え、エージェントは直前に言ったことを、あなたに欠けていた文脈を補いながら、`GLOSSARY.md` の語彙を使って平易な言葉で説明し直します。これは事後の対処です。`/grill-with-docs` は事前の治療で、早い段階で合意した共通言語こそが、そもそも専門用語が飛び交うのを防ぎます。
- **`/teach`**: 現在のディレクトリを状態付きワークスペースとして使用し、複数セッションにわたって概念を学習します。
- **`/writing-for-agents`** は、エージェントが読む文書を書くためのリファレンスです: スキル、AGENTS.md、ポインタで参照される文書などです。

## 前提条件

**`/setup-matt-pocock-skills`**: 最初のエンジニアリングフローの前に実行し、他のスキルが前提とする課題トラッカー、トリアージラベル、ドキュメント構造を設定します。カスタムの課題トラッカーにも対応しています。
