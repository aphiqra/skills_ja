# Test-Driven Development

TDDは red → green のループです。このスキルは、そのループが価値のあるテストを生み出すための基準を提供します：良いテストとは何か、テストをどこに書くか、アンチパターン、そしてループのルール。すべてのセクションはすべてのサイクルに適用されます — ループの後ではなく、前および実行中に参照してください。

コードベースを探索する際は、`CONTEXT.md` が存在する場合はそれを読み、テスト名やインターフェースの語彙がプロジェクトのドメイン言語と一致するようにします。また、対象領域のADRを尊重してください。

## What a good test is

テストは実装の詳細ではなく、公開インターフェースを通じて振る舞いを検証します。コードは完全に変更される可能性がありますが、テストは変わるべきではありません。良いテストは仕様書のように読めます — 「ユーザーは有効なカートでチェックアウトできる」は、どのような機能が存在するかを正確に示します — そして内部構造に依存しないため、リファクタリング後も維持されます。

例については [tests.md](tests.md)、モックのガイドラインについては [mocking.md](mocking.md) を参照してください。

## Seams — where tests go

**seam（縫い目）** とは、テストを行う公開境界のことです：内部に踏み込まずに振る舞いを観察できるインターフェースです。テストはseamに対して書かれ、内部実装に対して書いてはいけません。

**テストは事前に合意されたseamでのみ行います。** テストを書く前に、対象とするseamを書き出し、ユーザーと確認してください。確認されていないseamではテストを書いてはいけません。すべてをテストすることはできません — 事前にseamを合意することで、テストの労力が重要な経路や複雑なロジックに集中します。

問いかけ：「公開インターフェースは何か？どのseamをテストすべきか？」

## Anti-patterns

- **実装に密結合（Implementation-coupled）** — 内部の協力オブジェクトをモックしたり、privateメソッドをテストしたり、副経路（インターフェースではなくDBを直接参照するなど）で検証する。兆候：リファクタリングで振る舞いが変わっていないのにテストが壊れる。
- **自己言及的（Tautological）** — アサーションがコードと同じ方法で期待値を再計算している（`expect(add(a, b)).toBe(a + b)`、同じ方法で手計算したスナップショット、定数を自分自身と比較するなど）。この場合テストは構造上必ず成功し、コードと不一致になることがない。期待値は独立した正しい情報源（既知の正解リテラル、検証済みの例、仕様）から取得する必要がある。
- **水平スライス（Horizontal slicing）** — すべてのテストを書いてから実装を書く。大量に書かれたテストは「想像上の振る舞い」を検証してしまい、ユーザー視点の挙動ではなく形状をテストすることになる。その結果、変更に対して鈍感になり、実装理解前にテスト構造を固定してしまう。代わりに**縦断スライス（vertical slices）**で作業する — 1テスト → 1実装 → 繰り返し、それぞれのテストは前のサイクルで得られた知見に応じて更新される**トレーサーバレット**とする。

## Rules of the loop

- **Redの前にGreenはない。** まず失敗するテストを書き、その後にそれを通す最小限の実装を書く。将来のテストを先読みしたり、仮説的な機能を追加しない。
- **1スライスずつ進める。** 1つのseam、1つのテスト、1つの最小実装をサイクルごとに行う。
- **リファクタリングはループの一部ではない。** それはレビュー段階（`code-review` スキルを参照）で行うものであり、red → green の実装サイクルには含まれない。
