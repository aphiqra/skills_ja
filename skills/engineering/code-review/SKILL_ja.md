`HEAD` とユーザーが指定する固定点の差分を2軸でレビューします：

- **Standards** ― コードがリポジトリの文書化されたコーディング規約に準拠しているか？
- **Spec** ― コードが元の issue / PRD / 仕様を忠実に実装しているか？  

両軸は **並列サブエージェント** として動作し、互いのコンテキストを汚染しないようにした上で、このスキルが結果を集約します。  

issueトラッカーは提供されている想定です — `docs/agents/issue-tracker.md` が無い場合は `/setup-matt-pocock-skills` を実行してください。


## Process

### 1. 固定点の特定
  
ユーザーが言及したものをそのまま固定点として扱います — コミットSHA、ブランチ名、タグ、main、HEAD~5 など。指定が無い場合はユーザーに確認してください。  
差分コマンドを1回だけ確定します: git diff <fixed-point>...HEAD（三点リーダーによりマージベース比較）。さらに git log <fixed-point>..HEAD --oneline でコミット一覧も取得します。  
続行前に、固定点が解決できるか（git rev-parse <fixed-point>）、および差分が空でないかを確認します。無効な参照や空の差分はこの段階で失敗させます — 並列サブエージェント内で失敗させてはいけません。

### 2. 仕様の特定
  
元となる仕様を以下の順序で探します：
- コミットメッセージ内の issue 参照（#123, Closes #45, GitLab !67 など） — docs/agents/issue-tracker.md の手順で取得。
- ユーザーが引数として指定したパス。
- ブランチ名や機能に一致する docs/、specs/、.scratch/ 配下の PRD/仕様ファイル。
- 見つからない場合はユーザーに場所を確認します。「存在しない」と言われた場合は、**Spec** サブエージェントはスキップし、「no spec available」と報告します。

### 3. 規約の特定
  
コードの書き方を文書化したリポジトリ内のすべて（例: CODING_STANDARDS.md や CONTRIBUTING.md）。  
リポジトリの規約に加えて、Standards 軸は常に以下の **スメル基準** を含みます — Fowler のコードスメル（_Refactoring_, 第3章）に基づく固定セットです。次の2ルールに従います：
- **リポジトリ優先。** 文書化されたリポジトリ規約が常に優先され、基準が指摘する内容でも規約が許容する場合はスメルを抑制。
- **常に判断ベース。** 各スメルはあくまでヒューリスティック（例: "possible Feature Envy"）であり厳密な違反ではない — この基準でもツールで自動的に検出される項目は除外する。  
各スメルは「内容」と「修正方法」で説明されます。差分に照らして確認してください：
- **Mysterious Name** — 機能や用途が分からない名前。→ リネームする；適切な名前が付けられない場合は設計が不明確。
- **Duplicated Code** — 同じロジックが複数箇所に存在。→ 共通化して呼び出す。
- **Feature Envy** — 他オブジェクトのデータに過度に依存するメソッド。→ 対象へ移動。
- **Data Clumps** — 同じ引数の組が繰り返し登場。→ 型としてまとめる。
- **Primitive Obsession** — ドメイン概念をプリミティブで表現。→ 専用型を作る。
- **Repeated Switches** — 同じ条件分岐が複数箇所。→ ポリモーフィズム等に置き換え。
- **Shotgun Surgery** — 一変更で多くの箇所を修正。→ 変更を一箇所に集約。
- **Divergent Change** — 1モジュールが複数理由で変更。→ 分割する。
- **Speculative Generality** — 将来用の過剰な抽象化。→ 削除。
- **Message Chains** — 長いメソッドチェーン。→ 抽象化して隠す。
- **Middle Man** — 中継だけの構造。→ 直接呼び出す。
- **Refused Bequest** — 継承を活用していない。→ 合成へ変更。

### 4. 並列サブエージェントの起動
  
1つのメッセージで2つのエージェント呼び出しを送信します。両方とも汎用サブエージェントを使用してください。  
**Standards サブエージェントのプロンプト** — 以下を含める：
- 差分コマンドとコミット一覧。
- 見つかった規約ファイル、およびスメル基準全文。
- 指示：「各違反とスメルを報告。規約違反は明確に、スメルは判断ベースとして区別。」  
**Spec サブエージェントのプロンプト** — 以下を含める：
- 差分コマンドとコミット一覧。
- 仕様内容。
- 指示：「欠落、過剰実装、誤実装を報告。」  
仕様が無い場合は Spec サブエージェントをスキップします。

### 5. 集約
  
結果を ## Standards と ## Spec の見出しでそのまま提示し、統合や順位付けはしません。  
最後に1行要約：各軸の件数と最大の問題。

## Why two axes
  
変更は片方だけ通る場合があります：
- 規約は守るが内容が誤り → **Standards合格, Spec不合格**
- 内容は正しいが規約違反 → **Spec合格, Standards不合格**  
分離により片方がもう片方を覆い隠すことを防ぎます。
