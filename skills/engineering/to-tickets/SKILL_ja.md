# To Tickets

計画・仕様・または会話を **チケット** の集合に分解します — それぞれは縦方向のトレーサー弾（tracer‑bullet）となるスライスであり、どのチケットに“ブロックされているか”を明示する。

課題トラッカーおよびトリアージラベルの語彙は提供されているはずです — 提供されていない場合は `/setup-matt-pocock-skills` を実行してください。

## Process

### 1. コンテキストの収集

会話コンテキストにすでに存在する情報をもとに作業します。ユーザーが参照（仕様のパス、課題番号、URLなど）を引数として渡している場合は、それを取得し、本文およびコメント全文を読み取ってください。

### 2. コードベースの探索（任意）

まだコードベースを探索していない場合は、現在のコードの状態を理解するために探索してください。チケットのタイトルや説明では、プロジェクトのドメイン用語を使用し、対象領域に関連するADRを尊重してください。

実装を容易にするためのリファクタリングの機会を探してください。「変更を簡単にする変更を先に行い、その後に簡単になった変更を行う」。

### 3. 縦断スライスのドラフト作成

作業を **トレーサーバレット** のチケットに分解します。

<vertical-slice-rules>

- 各スライスは、すべてのレイヤー（スキーマ、API、UI、テスト）を横断する狭いが完全な経路である — 横方向の一層ではなく縦断スライス
- 完了したスライスは単体でデモまたは検証可能である
- 各スライスは、新しいコンテキストウィンドウ1つに収まるサイズである
- リファクタリングが必要な場合は最初に行う

</vertical-slice-rules>

各チケットには **ブロッキングエッジ**（開始前に完了している必要のあるチケット）を記述します。
ブロッカーがないチケットはすぐに開始できます。

**大規模リファクタリングは縦断スライスの例外です。**
**大規模リファクタリング**とは、1つの機械的変更（カラム名変更、共有シンボルの型変更など）であり、その影響範囲がコードベース全体に広がるため、1つの変更で多数の呼び出し箇所が壊れてしまい、単一の縦断スライスではグリーン状態を保てないものを指します。
これを無理にトレーサーバレットに分解せず、**expand–contract**で進めます。

まずexpand：旧形式と並行して新形式を追加し、何も壊さない状態にします。

次に移行：影響範囲に応じて（パッケージ単位、ディレクトリ単位など）呼び出し箇所を段階的に移行します。各バッチはexpandに依存するチケットとし、旧形式が残っているためCIは維持されます。

最後にcontract：すべての呼び出しが移行後、旧形式を削除します。このチケットはすべての移行バッチに依存します。

バッチでも単独でグリーンが保てない場合は、同様の順序を維持しつつ統合ブランチを共有し、最終の統合・検証チケットですべてをブロックし、そこでのみグリーンを保証します。

### 4. ユーザーへの確認

提案する分解案を番号付きリストで提示します。各チケットについて以下を示します：

- **Title**: 簡潔で説明的な名称
- **Blocked by**: 先に完了している必要のあるチケット
- **What it delivers**: このチケットで実現されるエンドツーエンドの振る舞い

ユーザーに以下を確認します：

- 粒度は適切か？（粗すぎる／細かすぎる）
- ブロッキングエッジは正しいか？（本当に依存しているもののみに限定されているか）
- チケットの統合または分割は必要か？

承認されるまで繰り返します。

### 5. チケットをトラッカーに公開

承認されたチケットを公開します。方法は `/setup-matt-pocock-skills` で設定されたトラッカーによって異なります — チケットの内容は同じで、依存関係の表現方法のみ異なります：

- **ローカルファイル** → `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 配下にチケットごとに1ファイル作成し、依存順（ブロッカーが先）で `01` から番号付けします。各ファイルの「Blocked by」は依存する番号/タイトルを記述します。以下のテンプレートを使用し、必ず1チケット1ファイルにしてください。
- **実トラッカー（GitHub、Linearなど）** → 依存順で課題を作成し、ネイティブな依存関係または「Blocked by」に他チケットを記述します。特別な指示がない限り `ready-for-agent` ラベルを付与してください。

**フロンティアを進める**：ブロッカーがすべて完了しているチケットから着手します。直線的な依存関係の場合は上から順に進めます。

親課題はクローズまたは変更しないでください。

<local-ticket-template>

# <NN> — <Ticket title>

**What to build:** ユーザー視点で、このチケットにより実現されるエンドツーエンドの振る舞い（レイヤー別の実装手順ではない）。

**Blocked by:** このチケットの前提となるチケットの番号/タイトル、または「None — can start immediately」。

**Status:** ready-for-agent

- [ ] Acceptance criterion 1
- [ ] Acceptance criterion 2

</local-ticket-template>

<issue-template>

## Parent

## What to build

- [ ] Criterion 2

</issue-template>

いずれの場合も、具体的なファイルパスやコードスニペットは避けてください（すぐに古くなるため）。
例外として、構造（状態機械、スキーマ、型など）を正確に示す必要がある場合に限り、重要部分のみを簡潔に含め、プロトタイプ由来であることを記載してください。

フロンティアに従い、`/implement` を用いてチケットを1つずつ進め、各チケットごとにコンテキストをリセットしてください。
