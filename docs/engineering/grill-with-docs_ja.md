## 機能

`grill-with-docs` は、計画や設計について、あなたと [agent](https://www.aihero.dev/ai-coding-dictionary/agent) が 1 つの共通理解を持てるまでインタビューを行い、その間に語彙と難しい決定をリポジトリに書き込みます。[grill-me](https://aihero.dev/skills-grill-me) が行うのと同じインタビュー（1 ラウンドの質問、待つ、次のラウンド）を、コードベースに向けたものです。

これは **[stateful](https://www.aihero.dev/ai-coding-dictionary/stateful)** です。他のグリル系スキルは [session](https://www.aihero.dev/ai-coding-dictionary/session) の内容をあなたの頭の中に残すだけですが、このスキルはディスク上にファイルを残します。用語が決まると、スキルは最後にまとめてではなく、すぐにそれを `GLOSSARY.md` に書きます。決定が 3 つの関門を通過すると、スキルはそれを ADR として書きます。違いはそれだけですが、人々がこのスキルで抱える問題のほとんどもそこから生じます。成果物は本物のリポジトリにある本物のファイルなので、あると思っていたのになかったり、複数の人が書くうちにずれていったりします。

## この機能を使うタイミング

これは `/grill-with-docs` と入力して呼び出します。エージェントが自分から使うことはありません。

リポジトリで変更を始めるとき、計画がまだぼんやりしていて、それを表す言葉もまだ決まっていない段階で使います。これは 1 セッション用のツールです。どのグリル系スキルが必要かは、目の前にあるものによって決まります:

| 手元にあるもの | 使うもの |
| --- | --- |
| そもそも作業ディレクトリで作業していない | [grill-me](https://aihero.dev/skills-grill-me) |
| リポジトリと、1 セッションで決着できる変更 | `grill-with-docs` |
| 1 セッションでは抱えきれない取り組み（新規のビルド、大きな機能） | [wayfinder](https://aihero.dev/skills-wayfinder) |
| ドメインの文書がまったくないリポジトリで、特に考えている機能はない | 変更ではなくリポジトリに向けた `grill-with-docs` |
| 別の誰かの頭の中にある知識が必要で止まっている決定 | [to-questionnaire](https://aihero.dev/skills-to-questionnaire) |

wayfinder との分かれ目はセッションの数です: 1 セッションの計画には `/grill-with-docs`、複数セッションの計画には `/wayfinder` を使います。

## 前提条件

このスキルはリポジトリに書き込むので、書き込んでも安全な場所にいる必要があります。決まった用語は、ルートの `GLOSSARY.md` という用語集に入ります。ルートにある `GLOSSARY-MAP.md` がそのリポジトリをマルチコンテキストと示している場合は、該当するコンテキストの `GLOSSARY.md` に入ります。決定は `docs/adr/` に入ります。スキルはどちらも必要になったときにだけ作成します。最初の用語か決定が決まるまでは何も存在しないので、前もって準備するものはありません。

また、他の 2 つのスキルが入っている必要があります。このスキル自身の `SKILL.md` は、それらに委譲する 1 行だけだからです。[grilling](https://aihero.dev/skills-grilling) がインタビューを、[domain-modeling](https://aihero.dev/skills-domain-modeling) が書き込みを担当します。`grill-with-docs` だけをインストールしても、動かないスキルが手に入るだけです。

## 記録として残るもの

セッションからは 3 種類のものが出てきますが、それらは同等ではありません。

| 決まったもの | 行き先 |
| --- | --- |
| 用語: ある物を表すプロジェクト独自の言葉 | 決まった瞬間に、その場で `GLOSSARY.md` へ |
| 元に戻しにくく、背景なしでは意外で、本物のトレードオフである決定 | `docs/adr/` 配下の ADR |
| それ以外に決めたすべてのこと | 会話の中だけ。他のどこにも残りません |

引っかかりやすいのは 3 行目です。`GLOSSARY.md` は用語集でしかありません。実装の詳細も、[spec](https://www.aihero.dev/ai-coding-dictionary/spec) も、メモ書きも入りません。ADR には 3 つの条件すべてが同時に必要なので、ほとんどの決定は当てはまらず、ほとんどのセッションでは ADR は 1 つも生まれません。用語集が磨かれ、ADR がゼロというセッションは設計どおりに機能していますが、それは合意したことのほとんどが、合意したときの [context window](https://www.aihero.dev/ai-coding-dictionary/context-window) の中にしか存在しないということでもあります。その会話は [clearing](https://www.aihero.dev/ai-coding-dictionary/clearing) せずに、そのまま [to-spec](https://aihero.dev/skills-to-spec) に渡してください。

主な成果物は用語集です。このスキルはドメインの言葉を作ります: 一度合意すれば、あなたもエージェントも同僚も二度と考え直さなくて済む、プロジェクト独自の言葉です。これがエージェントの性能を上げるかどうかについては、全員が同意しているわけではありません。最も強い反論は、用語とその平易な英語での言い換えは [model](https://www.aihero.dev/ai-coding-dictionary/model) から同じ結果を引き出すので、語彙は主にそれを共有する人間同士のコミュニケーションを短くするだけだ、というものです。その見方でも用語集には価値がありますが、その価値を受け取るのは人間です。

## よくある質問

**これと `/wayfinder` のどちらを使うべきですか？**
範囲で決まります。1 セッションで決着できるものにはこれを使い、1 セッションでは抱えきれない取り組みには [wayfinder](https://aihero.dev/skills-wayfinder) を使います。wayfinder はまず作業を意思決定の [tickets](https://www.aihero.dev/ai-coding-dictionary/ticket) のマップとして描きます。wayfinder はより遅く密度が高いので、範囲の明確な機能に使ってしまうのがよくある間違いです。これはこのスキルを置き換えるものではなく、マップの中でグリルに向いた部分については、グリルのセッションを始めることもできます。

**実行したのに、`GLOSSARY.md` も ADR もできませんでした。**
既知の原因が 2 つあります。1 つ目は、条件を満たすものがなかったことです。ADR には 3 つの関門すべてが必要で、新しい語彙のない変更についてのセッションなら、書くものがありません。2 つ目は本物のバグです。スキルが別のオーケストレーション層（spec 駆動開発のラッパー、マルチエージェントのフレームワーク、他人のパイプラインの 1 ステップとしてこれを呼び出すルールなど）の中で動くと、インタビューは行われるのに、ファイルを書く部分が黙って行われないとユーザーから報告されています。このバグは登録済みで、修正されていません。そういう構成で使っているなら、セッションの出力を信じる前に作業ディレクトリを確認してください。

**推奨もなしにすべてを一度に質問され、`GLOSSARY.md` には一切触れませんでした。**
それは、スキルが 2 つの依存先を読み込めていない状態です。`SKILL.md` は 1 行の委譲なので、[grilling](https://aihero.dev/skills-grilling) と [domain-modeling](https://aihero.dev/skills-domain-modeling) を読み込まなかったエージェントは、グリルとは何かを推測するしかなく、構造のないまま全部の質問が一度に来ます。一部だけ読み込まれた場合はもっと分かりにくくなります。`grilling` は読み込まれ、`domain-modeling` は読み込まれないと、良いインタビューが行われるのに記録は何も残りません。どのくらい起きるかはモデルと [effort](https://www.aihero.dev/ai-coding-dictionary/effort) のレベルによって変わり、これはこのスキルで最も多く報告されている問題です。疑わしいときは、どのスキルを読み込んだかをエージェントに直接尋ねてください。

**他の決定はすべてどこへ行ったのですか？**
会話の中だけです。これはこのスキルに対する最も深刻な未解決の不満です。用語集は spec ではなく、ほとんどの答えは ADR に値せず、決まった各回答を spec、チケット、テストに結びつける記録もありません。後のステップで、正確な答え（順序の保証、否定形の要件、数値のデフォルトなど）がぼやけた文章に弱められ、結果は完成しているように見えても、あなたが決めたことが抜けていることがあります。今のところは、セッションを残したまま、すぐに [to-spec](https://aihero.dev/skills-to-spec) に渡してください。そして、spec がそれらを取り込んだと決めつけず、自分の答えと照らし合わせて spec を読み直してください。

**文書がまったくない既存のリポジトリに使えますか？**
はい。ADR もドメインの言葉も設計原則もないコードベースには、これが適したスキルです: 呼び出して「help me document my repo」と言ってください。`GLOSSARY.md` を作ったり直したりするために、[improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) と組み合わせて使うユーザーも多いです。舵取りが必要になると思ってください。スキルはコードを読み、見つけたものについてあなたに尋ね、コードベースにすでにある言葉のどれが正しいかはあなたが決めます。

**セッションが終わったら何をすればいいですか？**
スキルの最後のメッセージはしばしば締まりのないものになり、これは既知の問題です。メインフローでの答えは、同じ会話のまま [to-spec](https://aihero.dev/skills-to-spec) に進むことです。変更がすぐに作れるほど小さければ、代わりに [implement](https://aihero.dev/skills-implement) に直接進んでください。

**なぜこういう名前なのですか？**
誰もこの名前に満足していません。挙動をより正確に表す `grill-domain-model` に改名する提案が出ていますが、何も進んでいません。もし改名されれば、docs ページもそれに合わせて移動し、URL も変わります。

## 正常に機能している場合

- `GLOSSARY.md` が最後に一塊で現れるのではなく、セッションの*最中に*、用語ごとに変わっていく。
- 用語集が純粋な語彙（プロジェクトの言葉と、引き締まった定義）として読め、実装の詳細や spec のような文章を含んでいない。
- コードベースから答えられる質問は、あなたに尋ねるのではなく、コードベースを読んで答えている。
- ADR はほとんど、あるいはまったく生まれず、生まれたものは、もう一度議論させられたら腹が立つような決定である。
- 既存の用語集で別の定義になっているという理由で、あなたが使った言葉に異議を唱える。

## この機能の位置付け

`grill-with-docs` はメインのビルドチェーンの先頭です:

```txt
grill-with-docs → to-spec → to-tickets → implement → code-review → retro
```

何かが spec として書かれる前に来ます。共通理解と確定した語彙を生み出し、[to-spec](https://aihero.dev/skills-to-spec) は改めてインタビューせずにそれをまとめます。近い隣人は、リポジトリもファイルもない同じインタビューである [grill-me](https://aihero.dev/skills-grill-me) と、このスキルが駆動する用語集と ADR の規律である [domain-modeling](https://aihero.dev/skills-domain-modeling) です。どちらもインタビューには [grilling](https://aihero.dev/skills-grilling) のプリミティブを使います。その上流では、[wayfinder](https://aihero.dev/skills-wayfinder) が 1 セッションには大きすぎる取り組みを描き、マップの一部をこのスキルに戻すことがあります。どのスキルやフローが合うか分からないときは、[ask-matt](https://aihero.dev/skills-ask-matt) が案内します。
