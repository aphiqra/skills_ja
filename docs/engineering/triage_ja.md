## 機能

`triage` は、プロジェクトのトラッカーにある issue を処理していきます。それぞれを、**トリアージロール**（カテゴリのロールと状態のロール）からなる小さな状態機械に沿って進めます。各 issue は最終的に、エージェントが着手できるブリーフ、報告者への具体的な質問、または理由を記録したうえでクローズされた issue のどれかになります。

これは**あなたが作成していない** issue のためだけのものです。つまり、未整理のバグ報告、届いた機能リクエスト、予告なく届いた外部のプルリクエストなど、外部からトラッカーに入ってきて、報告者が残した形のままになっている作業です。[to-tickets](https://aihero.dev/skills-to-tickets) の [Tickets](https://www.aihero.dev/ai-coding-dictionary/ticket) はすでにエージェントが着手できる状態なので、それに `triage` を実行すると作業が無駄になります。ルールは単純です: `/triage` は届いた issue のためだけのもので、自分で作成した issue のためのものではありません。

手作業でのラベル付けとも異なり、推奨をしてから待ちます。カテゴリと状態についての判断を理由とともに示し、コードベースで見つけたことも伝えますが、あなたが指示するまで何も適用しません。

## この機能を使うタイミング

これは `/triage` と入力し、続けてしたいことを普通の言葉で説明して呼び出します。[agent](https://www.aihero.dev/ai-coding-dictionary/agent) が自分から使うことはありません。例: 「対応が必要なものを見せて」、「#42 を見てみよう」、「#42 を ready-for-agent にして」。

| 手元にあるもの | 行き先 |
| --- | --- |
| 他の人からの未整理の報告でいっぱいのトラッカー | `/triage` |
| 自分のおおまかなアイデアがあるだけで、何も書いていない | [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| [spec](https://www.aihero.dev/ai-coding-dictionary/spec) にしたい、決着のついた会話 | [to-spec](https://aihero.dev/skills-to-spec) |
| エージェントが着手できるチケットに分けたい spec | [to-tickets](https://aihero.dev/skills-to-tickets) |
| ラベルではなく根本原因が必要な、確認済みのバグ | [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs) |

## 前提条件

`triage` は issue tracker を読み書きするので、先に [setup-matt-pocock-skills](https://aihero.dev/skills-setup-matt-pocock-skills) がそのトラッカーとラベルの語彙を設定している必要があります。下のロール名は**正規の**ものです。トラッカーのラベルの文字列はこれと異なることがあり、セットアップがその対応を提供します。トラッカーがすでに正規の名前をそのまま使っているなら、対応させるものもセットアップするものもありません。

トラッカーの設定では、外部のプルリクエストをリクエストの窓口として扱うかどうか、そして誰を外部とみなすかも決まります。そのフラグはデフォルトでオフで、セットアップはもうそれについて尋ねません。PR を対象に含めるには、`docs/agents/issue-tracker.md` でオンにしてください。

## 状態機械

トリアージされたすべての項目は、ちょうど 1 つのカテゴリのロールと 1 つの状態のロールで終わります。カテゴリは 2 つあります: `bug`（何かが壊れている）と `enhancement`（新機能や改善）です。状態は 5 つあります:

| 状態 | 意味 |
| --- | --- |
| `needs-triage` | あなたが評価する必要がある。ラベルのない issue は通常まずここに入る。 |
| `needs-info` | 報告者の返答待ち。返答があると `needs-triage` に戻る。 |
| `ready-for-agent` | 完全に仕様が決まり、エージェント向けのブリーフが付いている。[AFK](https://www.aihero.dev/ai-coding-dictionary/afk) のエージェントが引き受けられる。 |
| `ready-for-human` | 同じブリーフに加えて、エージェントにできない理由が書かれている: 判断、外部へのアクセス、手動でのテストなど。 |
| `wontfix` | 理由を記録したうえでクローズされた。 |

語彙はこれですべてです。1 項目につき状態のロールはちょうど 1 つというルールが、検索を単純に保ちます。状態は、この [skill](https://www.aihero.dev/ai-coding-dictionary/skill) で最も要望の多い部分でもあります。ユーザーからは、仕様は決まっているが別の issue にブロックされている作業のための状態、将来のきっかけを待つ作業のための `deferred` 状態、終端の `implemented` 状態が求められています。どれも出荷されていません。下の質問を参照してください。

`wontfix` には 3 つのケースがあります。知識ベースに書き込むのはそのうち 1 つだけなので、違いが重要です:

| クローズする理由 | 起きること |
| --- | --- |
| すでに実装されている | 機能がすでにどこにあるかを指すコメント。却下されたものではなく作られた機能なので `.out-of-scope/` には何も入りません。そこにファイルがあると重複チェックが壊れるからです。 |
| 却下されたバグ | 丁寧な説明をしてからクローズする。 |
| 却下された機能拡張 | `.out-of-scope/` にファイルを作り、クローズのコメントからリンクしてからクローズする。 |

`.out-of-scope/` には、issue ごとではなく、却下された**概念**ごとに Markdown ファイルが 1 つ入っています。各ファイルはデータベースの行ではなく、短い設計文書です。何が却下されたか、なぜか、そしてそれを求めたすべての issue が書かれています。`triage` は何かを評価する前にディレクトリ全体を読みます。キーワードではなく概念で照合するので、「night theme」は `dark-mode.md` に一致します。一致するものが見つかると、リクエストを一から議論し直す代わりに、以前の決定を見せて、今もそれに同意するかを尋ねます。

## ブリーフを書く前に検証する

[grilling](https://www.aihero.dev/ai-coding-dictionary/grilling) の前に、`triage` は主張が成り立つかを確認します。バグなら、報告者の手順から再現します。PR なら、ブランチをチェックアウトして関連するテストを実行します。その後、次の 3 つの結果のどれかを報告します:

- 確認できた。コードの経路も示す。
- 再現できなかった。
- 試すのに十分な詳細がない。これは `needs-info` の最も強い合図です。

同じ流れで、コードベースに対してさらに 2 つの確認を行います。**重複**の確認は、その機能がすでに実装されていないかを問い、報告者の言い回しではなくドメインの概念で検索します。**以前の却下**の確認は、`.out-of-scope/` がすでにノーと言っていないかを問います。どちらの確認も安く済み、どちらかに当たれば `wontfix` になります。

この作業のすべては、1 つの成果物を良いものにするためのものです: **エージェントブリーフ**です。issue が `ready-for-agent` に移るときに `triage` が投稿する、構造化されたコメントです。`triage` がそれを投稿した後は、ブリーフが契約であり、元の報告はただの背景情報になります。issue はコードが変わる間に何週間も `ready-for-agent` に置かれることがあるので、ブリーフは正確さより**長持ち**することを重視します。そのためブリーフは型、シグネチャ、振る舞いの契約を名指しし、ファイルパスや行番号は決して書きません。確認済みの再現があるブリーフは、推測に基づくブリーフよりずっと強力です。

## PR はコード付きの issue である

トラッカーが外部のプルリクエストをリクエストの窓口として扱うなら、それらも同じカテゴリ、状態、遷移を持つ同じ状態機械を通ります。状態は差分に対して適用されます。`ready-for-agent` は、ブリーフが付いていて、エージェントがコードについて次のステップを進めるべきだという意味です。`ready-for-human` は、人がマージできるという意味です。PR に付けるブリーフは、物をゼロから作る方法ではなく、既存の差分に対して残っている作業を説明します。

協力者の進行中のブランチはトリアージの作業ではないので、一覧の表示には*外部の* PR だけが現れます。その絞り込みは一覧の表示にだけ適用されます。PR を明示的に指定すれば、誰が書いたものでも `triage` は扱います。

## よくある質問

**`/to-spec` と `/to-tickets` を実行したら、そのチケットがトリアージされないまま残っています。`/triage` を実行すべきですか？**
いいえ。それらはすでにエージェントが着手できる状態です。`to-tickets` は公開時に `ready-for-agent` ラベルを付けるので、AFK のランナーはもう一度処理しなくてもそれを拾います。これに出くわしたユーザーは、spec のフローを実行して出力に `needs-triage` が付いているのを見ていて、その AFK のランナーはすべてを無視していました。`triage` は外部から届く作業のためのオンランプです。spec のフローは、自分で始める作業のための車線です。両者は `ready-for-agent` で合流し、それより前では交わりません。

**`to-spec` → `to-tickets` → `implement` のフローができた今でも、`triage` は意味がありますか？**
外から届く作業があるならです。`triage` はそのフローより古く、別の仕事をします: 他の人が登録した報告を扱うことです。トラッカーにあるものがすべて自分の計画から来たものなら、使うことはめったにありません。何か公開のものを保守していたり、チームがあなたにバグを登録したりするなら、そこが作業の出発点です。主な用途は、外部の貢献者から issue を受け付けるオープンソースのリポジトリです。

**エージェントが `ready-for-agent` を付けようとしたら、`gh` にそのラベルは存在しないと言われました。**
これは既知の未解決のバグです（[#616](https://github.com/mattpocock/skills/issues/616)）。`setup-matt-pocock-skills` はラベルの語彙を `docs/agents/triage-labels.md` に書きますが、トラッカーにラベルは作りません。5 つの状態ラベルと 2 つのカテゴリラベルを、`gh label create` かトラッカーの UI で一度だけ自分で作れば、エラーは止まります。その issue には、マージされていないコミュニティの修正ブランチへのリンクがあります。

**5 つの状態では足りません。blocked、deferred、implemented はどうですか？**
これはこのスキルで最も多く登録されている不足です。3 つの形で現れます:

- 完全に仕様が決まっているが、別の issue がクローズされるのを待っている issue（[#139](https://github.com/mattpocock/skills/issues/139)）。報告者は、そこでの `ready-for-agent` は「技術的には正しい」が誤解を招くと述べており、エージェントがそれを拾って行き詰まってしまいます。
- 意図はあるが、きっかけを待っているのでまだ着手できない将来の作業（[#297](https://github.com/mattpocock/skills/issues/297)）。
- 「実装済み、検証待ち」を表す終端の状態。これがないと、AFK のランナーが完了したチケットを再びキューに入れてしまうことがあります。

blocked のケースは本物の問題として受け入れられていますが、名前（`blocked` か `paused` か）が決まっていません。どれも出荷されていません。回避策として、カテゴリの横にリポジトリ独自の追加ラベルを付ける人がいます。そうすれば状態の枠には正確な値が入りますが、スキルはその追加ラベルについて何も知りません。あるコミュニティのフォークはさらに進んで、`needs-slicing`、`tracking`、作業量のラベルを追加しています。それは機能しますが、スキルではなくそのフォークのものです。

**`/diagnosing-bugs` とどう違うのですか？**
ここでの検証のステップは意図的に浅くしてあります。「これは本物か、だいたいどこにあるか」に答えるもので、根本原因は探しません。報告者の手順で数分以内にバグが再現しなければ、`needs-info` を使うか、今すぐ調べたいなら [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs) を使ってください。どちらのスキルの本文も、まだもう一方に触れていません。あるユーザーがその不足を報告しており、まだ未解決です。

**バックログ全体を指定して、そのまま実行させられますか？**
頼むことはできますが、何を読んでいるかに注意してください。「対応が必要なものを見せる」処理は、*選ぶため*の安い一覧です。あなたが 1 つの issue を選び、それから `triage` がその issue について完全な [context](https://www.aihero.dev/ai-coding-dictionary/context) を集めます。20 個の issue に一度に実行すると、エージェントがその安い一覧を唯一の証拠として、何も言わずに使ってしまうことがあります。その一覧は issue の本文は返しますが、コメントは返しません。あるユーザーがまさにこれに出くわしました。3 つの issue にはすでに「修正済み、クローズを推奨」というコメントが付いていたのに、3 つとも新しいエージェントブリーフが付けられました。まとめて処理するときは、各 issue のコメントを読むよう明示的に伝えてください。

**Linear など、GitHub Issues 以外でも使えますか？**
はい。トラッカーはハードコードされた前提ではなく設定です。Linear（`linear` CLI 経由）、GitLab、`.scratch/` 配下の普通の Markdown ファイルで実行している人がいます。よくある分け方は、issue と計画には Linear、コードと PR には GitHub を使うことです。そうすると「issue tracker」と言うスキルは Linear に、「PR」と言うスキルは GitHub に対応します。ローカルの Markdown のトラッカーには未解決のテンプレートのバグがあります: 生成されたファイルに、受け入れ条件が最上位とエージェントブリーフの中の 2 回含まれることがあります（[#200](https://github.com/mattpocock/skills/issues/200)）。

## 正常に機能している場合

- 触れたすべての項目が、ちょうど 1 つのカテゴリのロールと 1 つの状態のロールで終わり、ゼロのことも、食い違う 2 つの状態を持つこともない。
- 理由を添えて推奨を示し、そこで止まる。issue のラベルを付け替えて先に進むことはしない。
- 何かが `ready-for-agent` になる前に、バグを再現したか、PR をチェックアウトして実行している。
- 書いたブリーフが型と振る舞いを名指しし、ファイルパスや行番号を含んでいない。
- 半年前に却下したリクエストが戻ってくると、もう一度トリアージする代わりに、そのことを伝えて以前の理由を引用する。
- 投稿するすべてのコメントが `> *This was generated by AI during triage.*` で始まる。

## この機能の位置付け

`triage` は**オンランプ**であって、メインチェーンのステップではありません。メインフローは、あなたが持ったアイデアから始まります（グリル、spec、チケット、実装、レビュー）。`triage` は、他の誰かから来た作業のための並行した車線です。どちらの車線も同じ場所で終わります: ブリーフ付きで `ready-for-agent` とラベル付けされた issue です。[implement](https://aihero.dev/skills-implement) は、[to-tickets](https://aihero.dev/skills-to-tickets) のチケットを拾うのと同じ方法でそれを拾います。`triage` がブリーフを書く前にリクエストにさらに詳細が必要なときは、`triage` は [grilling](https://aihero.dev/skills-grilling) と [domain-modeling](https://aihero.dev/skills-domain-modeling) を一緒に、1 ラウンドずつ質問しながら実行するので、あなたが下した決定はその場で `GLOSSARY.md` と ADR に記録されます。どの車線にいるのか分からないときは、[ask-matt](https://aihero.dev/skills-ask-matt) が案内します。
