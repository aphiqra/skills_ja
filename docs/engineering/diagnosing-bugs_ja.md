## 機能

`diagnosing-bugs` は、難しいバグやパフォーマンスの退行に対して、6 つのフェーズからなる診断を行います: 再現手順を作る、それを最小化する、仮説を順位付けする、計測を仕込む、回帰テストとともに修正する、後片付けをする。

**厳密な**フィードバックループができるまで、エージェントに仮説を立てさせません。ループとは、名前の付いた 1 つのコマンドで、すでに一度実行されており、*このバグ*で失敗（red）し、修正されると成功（green）するものです。バグ報告を渡されたコーディングエージェントは、デフォルトではコードを読んで推測します。このスキルはそれを止めます。red にできるコマンドがなければ、フェーズ 2 はありません。この 1 つの関門こそがこのスキルの目的です。ループができてしまえば、その後のすべて（二分探索、仮説の検証、計測）は機械的な作業です。

## この機能を使うタイミング

`/diagnosing-bugs` と入力するか、タスクに合うときにエージェントが自分から使います。モデル起動型で、「diagnose」や「debug this」と言われたとき、または何かが壊れている、例外を投げる、失敗する、遅いという報告があったときに起動します。

難しいものに使ってください: 一見して解けないバグ、断続的な不具合、既知の正常な 2 つの状態の間で入り込んだ退行などです。意図的に遅く徹底的なので、1 回のメッセージで答えてほしい質問には不向きです。

| あなたの状況 | 行き先 |
| --- | --- |
| 症状として説明できる具体的な不具合 | このスキル |
| 遅いエンドポイントや、変更前後が分かっているタイミングの退行 | このスキル。パフォーマンス用の分岐があります（ベースラインを測ってから二分探索する） |
| 特定の症状はなく「このコードベースのボトルネックはどこ？」 | このスキルではありません。既知の 1 つの障害を診断するもので、監査はしません |
| 他の人からの未確認・未整理のバグ報告 | まず [triage](https://aihero.dev/skills-triage) |
| 不具合を追うのではなく、設計上の疑問に答えるための使い捨てコード | [prototype](https://aihero.dev/skills-prototype) |
| 計画した振る舞いをテストファーストで作る | [tdd](https://aihero.dev/skills-tdd) |
| 修正した後で、何がそのバグを防げたかを問う | 同じセッションで実行する [retro](https://aihero.dev/skills-retro) |
| バグを固定する良い seam が存在しない | [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture)。あなた自身が開始します |

## 厳密なループこそがこのスキル

フェーズ 1 に最も労力がかかるのは、それが唯一の難しいフェーズだからです。スキルはループを作る方法を、おおよそ優先度の高い順に挙げています:

1. バグに届く任意の seam での、失敗するテスト。
2. 起動中の開発サーバーに対する curl や HTTP スクリプト。
3. フィクスチャを入力にした CLI 呼び出しを、既知の正常なスナップショットと diff する。
4. DOM、コンソール、ネットワークに対してアサーションを行うヘッドレスブラウザのスクリプト。
5. 記録の再生: 保存したリクエスト、ペイロード、イベントログを、そのコード経路だけに通して実行する。
6. 使い捨てのハーネス: システムの最小限の部分集合、1 回の関数呼び出し。
7. 「ときどき出力が間違う」場合のための、プロパティテストやファジングのループ。
8. `git bisect run` に渡せる二分探索用のハーネス。
9. 差分ループ: 同じ入力で、古いバージョンと新しいバージョンを比べる。
10. 最後の手段としての [human-in-the-loop](https://www.aihero.dev/ai-coding-dictionary/human-in-the-loop) bash スクリプト。スキルにはそのための `scripts/hitl-loop.template.sh` が付属しています: エージェントがスクリプトを実行し、あなたはターミナルで指示に従い、あなたの回答が解析可能な出力として返ってきます。

目的はループが*ある*ことではありません。**厳密である**ことです: 速い（数秒）、決定的（毎回同じ判定）、鋭い（「クラッシュしなかった」ではなく、あなたの症状そのものをアサートする）、そしてあなたがいなくてもエージェントが実行できること。30 秒かかって不安定なループは、ないよりわずかにましな程度です。ときどきしか現れないバグでは、目標はきれいな再現ではなく**再現率を上げること**です: トリガーをループで回し、並列化し、負荷をかけ、sleep を挟んで、デバッグできるほど失敗率が高くなるまで続けます。

エージェントがループを作れない場合、スキルは止まってそう伝えるよう指示します。試したことを挙げ、[environment](https://www.aihero.dev/ai-coding-dictionary/environment) へのアクセス、記録済みの成果物、または一時的な計測を追加する許可をあなたに求めます。それでも仮説を立てに進むことは許されません。

## フェーズ間の関門

フェーズはチェックリストではなく関門です。特定の条件が満たされるまで、エージェントはそのフェーズに入れません。

| 関門 | 満たすべき条件 |
| --- | --- |
| フェーズ 2 へ | このバグで red になりうる、名前の付いたコマンドがあり、すでに実行されて出力とともに貼り付けられている |
| フェーズ 3 へ | 再現手順が再現され、*かつ*最小化されている: 残っている要素はすべてバグの再現に必要なものである |
| フェーズ 4 へ | 順位付けされた反証可能な仮説が 3〜5 個あり、それぞれが予測を述べていて、どれかを検証する前にあなたに示されている |
| フェーズ 5 へ | 検査が特定の予測に対応し、一度に 1 つの変数だけを変え、すべてのデバッグログに `[DEBUG-a4f2]` のようなタグが付いていて、後片付けのときに 1 回の grep ですべて見つかる |
| 完了 | 元の再現手順でもう再現せず、計測が取り除かれ、コミットメッセージに正しかった仮説が書かれている |

フェーズ 5 には 1 つ例外があります。エージェントは修正の前に回帰テストを書きますが、それはそのための**正しい seam** がある場合だけです。正しい seam とは、呼び出し箇所で起きるのと同じ形で、テストが本物のバグのパターンを動かせる場所です。使える seam が浅すぎる場合、スキルはエージェントに、誤った安心感を与えるテストを書く代わりにそう伝えるよう指示します。seam がないこと自体が発見であり、エージェントはそれを隠さずに記録します。

## よくある質問

**直接答えてほしいだけの簡単な質問でも起動してしまいます。**
これはこのスキルで最も多く報告されている問題です。特に GPT-5.6-Sol では、問題をただ説明しただけで起動すると報告されています: 「モデルが代わりに、かなり形式ばった diagnosing-bugs スキルを起動する。そして回答や提案をする前に、再現シナリオを組み立てる（たいてい価値の低いモックのシナリオを作る）。その結果、返答がかなり遅れる。」[issue #578](https://github.com/mattpocock/skills/issues/578) では 4 人が別々に同じ問題を報告しました。受け入れられた修正方針は、軽いアプローチから始めて、問題が必要とするときだけ完全な診断に移ることですが、その変更はまだ出荷されていません。このスキルは Claude Code の呼び出しの挙動に合わせて調整されているので、起動のしきい値が低い [model](https://www.aihero.dev/ai-coding-dictionary/model) では起動しすぎます。修正が出荷されるまでの回避策は、何をしてほしいかを伝える（「診断せずにこれに答えて」）か、[harness](https://www.aihero.dev/ai-coding-dictionary/harness) でこのスキルのモデル起動を無効にすることです。

**コードベースを指定して、パフォーマンスの問題がどこにあるか聞けますか？**
いいえ。これはすでに名前を挙げられる 1 つの障害を診断するものです。パフォーマンス用の分岐は、症状のある退行のためのもの（ベースラインの計測を確立してから二分探索する。先に測り、後で直す）であって、予防的な調査のためではありません。予防的な調査のためのスキルは [提案されてクローズされました](https://github.com/mattpocock/skills/issues/431)。今それを行うスキルはありません。

**修正を書く前に止まって確認してくれますか？**
いいえ。人間のチェックポイントがあるのはフェーズ 3 だけです: 順位付けした仮説の一覧が、どれかを検証する前にあなたに示され、あなたが不在ならエージェントは自分の順位で進めます。計測と修正の間に関門はないので、あなたが根本原因に同意する前に、エージェントがコードを書き始めることがあります。[Issue #124](https://github.com/mattpocock/skills/issues/124) がその関門を求めており、まだ未解決です。必要なら、スキルを呼び出すときにそう伝えてください。

**このバグ報告にはすでに `/triage` を実行しました。同じ作業をもう一度するのですか？**
部分的にはそうで、どちらのスキルもそのことを述べていません。ある読者はこう指摘しています: 「triage のステップ 3 は、本質的には diagnosing-bugs のフェーズ 1〜2 を浅く限定的に行うものだが、どちらのファイルももう一方に触れていない。」triage は「これは本当にバグか、影響範囲はどこか」を限定的に確認し、このスキルはその徹底版を行います。先に triage を実行しても無駄にはなりません。その検証で、フェーズ 1 の材料のほとんどが手に入ることが多いからです。ただし、このスキルがその作業を一から全部やり直すこと、そしてそれを知らせる相互参照がないことは覚悟しておいてください。

**貼り付けられる再現の出力から、秘密情報が漏れませんか？**
漏れる可能性はあります。スキルはエージェントに、実行したコマンドとその出力を貼り付けることと、HAR ファイル、ログのダンプ、コアダンプのような成果物を求めることを指示しています。それらをサニタイズするよう指示するものはありません。[Issue #674](https://github.com/mattpocock/skills/issues/674) がまさにこれ（チャット、issue、PR にコピーされる認証情報、トークン、Cookie、個人データ）を取り上げ、伏せ字にするガードレールを提案しています。未解決で、実装されていません。当面は、特に出力が公開の場所に出る前に、伏せ字にするのはあなたの仕事だと考えてください。

**セキュリティスキャナーがこのスキルを高リスクと判定しました。**
Snyk がそう判定しますが、誤検知です。これはセットの中で唯一、実行可能なシェルスクリプト（`hitl-loop.template.sh`）を、それを実行する指示や開発サーバーに curl する指示と一緒に同梱しているスキルです。同梱された `.sh` ファイル、それを実行する指示、外向きの HTTP がそろえば、静的スキャナーを反応させるには十分です。スクリプト自体は、人間の入力を待つ `read -r -p` のプロンプトが 30 行ほどあるだけです。スキャナーが評価しているのはスキルに可能なことであって、実証されたエクスプロイトではありません。

**`/diagnose` はどうなりましたか？**
v1.0.0 で `/diagnosing-bugs` に名前が変わりました。古い名前はもう存在しません。`/diagnose` を連鎖させているもの（ラッパーのスキル、保存したプロンプトなど）は更新が必要です。

## 正常に機能している場合

- 仮説を 1 つでも示す前に、コマンドとその red の出力を見せる。仮説が先に来るなら、スキルは動いていません。
- 再現する障害が、途中で見つけた近くの別の障害ではなく、あなたが報告したものである。
- 推測を始める前に再現手順を小さくし、残った各要素がなぜ必要かを説明できる。
- どれかを検証する前に、反証可能な予測を伴う 3〜5 個の仮説を順位付けして見せる。
- 追加するすべてのデバッグログに `[DEBUG-a4f2]` のようなタグが付いていて、完了を宣言したときにはそのタグで grep しても何も見つからない。
- コミットや PR のメッセージに、どの仮説が正しかったかが書かれている。
- テストでバグを固定できない場合、浅いテストを書く代わりにそう伝える。

## この機能の位置付け

`diagnosing-bugs` はいつでも使えるスタンドアロンです。何かが壊れたときに開始し、修正とその回帰テストが入ったところで終わります。状態を持たず、事前のセットアップも必要ありません。[ask-matt](https://aihero.dev/skills-ask-matt) は「何かが壊れている」をここへ案内します。

重要な隣人が 2 つあります。[retro](https://aihero.dev/skills-retro) はこの後に来ます: 修正が入ったら、セッションが開始時よりも多くの情報を持っているうちに、同じセッションで実行し、何がそのバグを防げたかを問います。`retro` はユーザー起動型なので、`diagnosing-bugs` が自分で `retro` を呼び出すことはありません。[triage](https://aihero.dev/skills-triage) は、他の人から未整理の報告として届いたバグについてこの前に来て、同じ最初の 2 フェーズを浅く行います。
