## 機能

`improve-codebase-architecture` は、コードベースを調べて**深いモジュール化の機会**（deepening opportunities）を探します。浅いモジュール（隠している中身とほとんど同じくらい複雑な interface を持つもの）を深いモジュールにできる場所のことです。見つけたものを自己完結した HTML レポートにまとめ、その後あなたが選んだものについて [grills](https://www.aihero.dev/ai-coding-dictionary/grilling) します。

コードを変更することは決してありません。実行全体で生まれるのは、会話と、OS の一時ディレクトリにある HTML ファイル 1 つだけです。リファクタリングは後で、別の [session](https://www.aihero.dev/ai-coding-dictionary/session) で、通常のビルドフローを通じて行います。そのためこれはリファクタリングのツールではなく調査であり、まだ手を付ける準備ができていないコードベースにも実行できます。

レポートがありきたりな掃除のアドバイスにならないよう、2 つのフィルターがあります。1 つ目に、すべての候補は**削除テスト**に合格しなければなりません: このモジュールを取り除いたら、その複雑さはより小さな interface の背後に移るのか、それとも呼び出し側に散らばるのか？カードになるのは前者の場合だけです。2 つ目に、特定の領域を指定しない限り、まず最近のコミット履歴を読み、頻繁に変わるパスに調査を絞ります。誰も触らないコードを深くしても、元が取れないリファクタリングになるだけです。

## この機能を使うタイミング

これは `/improve-codebase-architecture` と入力して呼び出します。[agent](https://www.aihero.dev/ai-coding-dictionary/agent) が自分から使うことはありません。

これはメインのビルドループのステップではありません。コードベースを改善する作業をさらに積んでおくために、定期的に実行します。使われる場面は 4 つあります:

| 場面 | 使い方 |
| --- | --- |
| 日常の保守 | 数日おき、または手が空いたときに実行し、機能開発の合間に構造が劣化しないようにする。 |
| 大きなビルドの前 | [spec](https://www.aihero.dev/ai-coding-dictionary/spec) を指定して「この変更を簡単にするにはどうすればいいか？」と尋ねる。これが最も効果的なプロンプトです。 |
| 既存コードの監査 | 大きく、構造がなく、[vibe-coded](https://www.aihero.dev/ai-coding-dictionary/vibe-coding) なリポジトリに実行して、どういう状態にあるかを把握する。 |
| レガシーコードのテスト作業 | テストできないコードにテストを書く前に、欠けている seam を見つけるために使う。 |

兄弟スキルと混同しやすい場面:

- すでに選んだ 1 つのモジュールを設計するなら、[codebase-design](https://aihero.dev/skills-codebase-design) を使ってください。このスキルは取り組むべきモジュールを見つけ、`codebase-design` でそれを設計します。
- 1 セッションでは抱えきれない取り組み全体には、[wayfinder](https://aihero.dev/skills-wayfinder) を使ってください。
- 「この特定のものが壊れている」なら、[diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs) を使ってください。バグを固定する良い seam がないことが本当の発見だった場合、そこからここに戻されます。

## 前提条件

実行に必要なものはありません。`GLOSSARY.md` や `docs/adr/` の ADR があれば、それを読んでドメイン独自の名詞を使います。そうすると候補は「FooBarHandler をリファクタリングする」ではなく、「Order intake モジュールを深くする」のように読めるようになります。

書き込む場所は 2 か所です。レポートはリポジトリの外の `<tmpdir>/architecture-review-<timestamp>.html` に出力されます。グリルのループの間には、`GLOSSARY.md` に用語を追加したり磨いたりし、ファイルがなければ作成します。また、却下した候補を ADR として記録することを提案するので、次回の実行でそれが再び提案されることはありません。

## depth と、それを探すレポート

このスキルは **depth** という 1 つの考え方に基づいています。深いモジュールは、小さく安定した interface の背後に多くの振る舞いを置きます。浅いモジュールは、その下にあるコードとほとんど同じくらい幅広い interface を通じて、実装をさらけ出します。レポートは 3 つの形の浅さを探します:

- テストしやすくするためだけに切り出された純粋関数で、本当のバグは呼び出し側の使い方にある（**locality** がない）。
- **seams** を越えて漏れているモジュール。
- 5 つのファイルを開かないと理解できない概念。

それぞれについて、それを直すための深くし方を提案します。

各候補は 1 枚のカードで、関係するファイル、摩擦、平易な英語での解決策、**locality** と **leverage** の観点での利点、変更前後の図、強さを示すバッジが載っています。

| バッジ | あなたにとっての意味 |
| --- | --- |
| `Strong` | 削除テストに明確に合格し、摩擦が本物である。真剣に検討してください。 |
| `Worth exploring` | 妥当な深くし方だが、効果はコードが今後どこへ向かうかによる。 |
| `Speculative` | 網羅性のために含めたもの。ほとんどは無視してかまいません。 |

レポートの最後には**Top recommendation**、つまり最初に取り組むべき候補が示されます。そこでスキルは止まり、どの候補を探りたいかを尋ねます。この時点では何も決まっておらず、コードも何も変わっていません。

## 候補を選んだ後に起きること

候補を選ぶと、それについての [grilling](https://aihero.dev/skills-grilling) のセッションが始まります。制約、seam の背後に何を置くか、どのテストが残るか、深くした interface がどうあるべきかを扱います。そのセッションの成果は差分ではなく決定です。そこからは通常のフローになります: 決定を [to-spec](https://aihero.dev/skills-to-spec) に持ち込み、次に [to-tickets](https://aihero.dev/skills-to-tickets)、そして [implement](https://aihero.dev/skills-implement) へ進みます。

## よくある質問

**選択肢を見せてくれる代わりに、1 つのアイデアについて 1 時間もグリルされました。オフにできますか？**

はい。呼び出すときにそう伝えてください（「グリルせずに、レポートだけ見せて」）。これはこのスキルについて最も多い不満です。あるユーザーは「改善点を徹底的に分析してもらう便利な方法」として気に入っていましたが、グリルのループが追加された後は「ほとんど使い物にならない」と感じました。そのユーザーのセッションでは、解決策を 1 つだけ提案し、その後「数十、数百の質問」をしてきたそうです。設計上の意図は、まずレポートが来て、グリルはあなたが選んだ候補についてだけ始まる、というものです。しかし弱い [models](https://www.aihero.dev/ai-coding-dictionary/model) は、最初に思いついたアイデアについてのインタビューにいきなり飛んでしまいます。そのスレッドでの結果はモデルによって大きく異なります。これは未解決の issue で、スキルにはまだ文書化されたグリルなしのモードがありません。

**レポートがスタイルのない生の HTML として開き、図もありませんでした。何が起きたのですか？**

レポートは Tailwind と Mermaid を CDN から読み込むので、開くときにネットワークへのアクセスが必要です。何かがそれらのスクリプトをブロックすると、エラーも出ずにページが崩れます。報告された事例では、セキュリティフックが SRI ハッシュを要求していました。エージェントはそれを追加しましたが、CDN がハッシュを計算した `curl` とブラウザに異なるバイト列を返したため、ブラウザがスクリプトをブロックしました。オフラインやロックダウンされた環境でも同じ問題が起きます。エージェントはページを描画しないので、これに気づけません。回避策として、CDN の構成ではなく、インラインの CSS と手作りの SVG の図を頼んでください。これは未解決の issue です。

**候補が 12 個出てきました。同じセッションで順に取り組むべきですか、それとも新しいセッションを始めるべきですか？**

1 セッションにつき 1 候補にしてください。1 つの会話で複数に取り組むと、[context window](https://www.aihero.dev/ai-coding-dictionary/context-window) がレポート、グリル、ドメインモデルの編集、コードの変更で一度にいっぱいになります。レポートはただの一時ファイルなので、引き継ぐのはファイルではなく候補です。1 つを選び、グリルし、決定を `/to-spec` に持ち込んでください。残りは後で別々に取り組める [tickets](https://www.aihero.dev/ai-coding-dictionary/ticket) にしておきます。選んだ改善は、直接実装に進むのではなく spec にしてください。これはよく聞かれますが、スキル自体にはそのためのワークフローが書かれていません。

**どうプロンプトを与えればいいですか？**

次に作るものをプロンプトにしてください。大きなビルドが控えているなら、spec を指定して「この変更を簡単にするにはどうすればいいか？」と尋ねます。プロンプトなしで実行すると、自分でホットスポットを探します。日常の保守ならそれで十分ですが、方向性を与えるとレポートが実行に移しやすいものになります。

**大きなレガシーコードベースでも機能しますか？**

部分的には機能します。一貫した構造のない大きな既存のコードベースではうまく機能し、一度きりの構造的なセットアップの後の保守ツールとして推奨されています。しかし、手に負えなくなったプロジェクトを持つユーザーは「少しは役に立ったが、まだ十分とは言えない」と報告しています。8 年もののレガシーコードベースを持つある開発者は、モデルが堂々巡りをしたと報告しましたが、同じスキルが整ったリポジトリではきれいなグラフを出します。そういうケース向けの専用の `/refactor` スキルはまだありません。コードベースに共通の語彙がなければ、まず [grill-with-docs](https://aihero.dev/skills-grill-with-docs) を実行して作ってください。そうすると、たいていこのスキルの出力がずっと良くなります。

**`/codebase-design` とどう違うのですか？**

`/codebase-design` はリファレンスであって、セッションを進めるドライバーではありません。語彙（module、interface、depth、seam、adapter、leverage、locality）を提供し、このスキルがそれを使います。新しいエージェントに `/codebase-design` をタスクとして与えると、決まった失敗の仕方をします。従うべき独自のプロセスがないので、エージェントはプロセスを作り出し、コードを再び調べ、何かを尋ねるまでに非常に長い時間がかかります。このスキルを実行し、それにあちらを使わせてください。

**コードベースは問題ないと言ってくれることはありますか？**

めったにありません。始める前にそのことを知っておいてください。このスキルは発見を出力するために存在するので、何も問題がないと結論づけるより、候補を出す傾向があります。それを補正するために強さのバッジを使ってください。レポートの候補がすべて `Speculative` なら、スキルは何も見つけなかったということです。

**Codex や他のハーネスでも機能しますか？**

部分的には機能します。調査のステップでは、Claude Code の `Agent` ツールを `subagent_type=Explore` で直接名指ししています。そのツールのない [harness](https://www.aihero.dev/ai-coding-dictionary/harness) では、自分の同等の機能を使う代わりに、並列の調査を飛ばしてしまうことがあります。スキルは動きますが、調査の徹底度は下がります。ハーネスに依存しない書き直しが提案されていますが、マージされていません。

**TypeScript で deep なモジュールを実際にどう実装すればいいですか？**

スキルには良い答えが入っていません。原則を具体的なファイルとモジュールの配置にした `TYPESCRIPT.md` がよく求められますが、存在しません。スキルは、深くし方がどこに属し、seam の背後に何を置くかを教えてくれます。それをパッケージやディレクトリの構造にするのは、あなた自身の仕事です。

## 正常に機能している場合

- 候補が、でっち上げたクラス名ではなく、ドメインの概念を名指ししている: 「FooBarHandler」ではなく「Order intake モジュール」。
- 候補が、誰も触らないリポジトリの部分ではなく、最近編集したファイルにある。
- 実行中にコードが何も変わらない。新しいファイルは一時ディレクトリにある HTML レポートだけである。
- レポートの後で止まり、どの候補がいいかを尋ねる。自分で先に進まない。
- 各カードが、ただ「こちらのほうがきれい」ではなく、効果を locality や leverage として説明し、どのテストが単純になるかを述べている。
- 長く続く理由で候補を却下すると、ADR を記録することを提案し、次回の実行でそれが再び提案されないようにする。

## この機能の位置付け

`improve-codebase-architecture` は**定期的な保守**です。どのチェーンにも属さずに数日おきに実行し、作業を行うのではなく、作業を積んでおきます。隣人:

- [codebase-design](https://aihero.dev/skills-codebase-design) は、すべての候補が使う depth と seam の語彙を担当します。
- [grilling](https://aihero.dev/skills-grilling) は、候補を選んだ後に判断のツリーをたどります。
- [domain-modeling](https://aihero.dev/skills-domain-modeling) は、決定を下す間、`GLOSSARY.md` と ADR を最新に保ちます。

その成果はアイデアであり、[grill-with-docs](https://aihero.dev/skills-grill-with-docs) か [to-spec](https://aihero.dev/skills-to-spec) でメインのビルドフローに戻ります。メインフローの終わりにある対応物は [retro](https://aihero.dev/skills-retro) です。このスキルはエージェントが作業するコードを改善し、`retro` はビルドの後で、その周りの環境（チェック、規約、ステアリングファイル）を改善します。状況にどのスキルが合うかについては、[ask-matt](https://aihero.dev/skills-ask-matt) がスキル全体を案内するルーターです。
