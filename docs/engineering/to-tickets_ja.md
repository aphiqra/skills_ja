## 機能

`to-tickets` は、計画、[spec](https://www.aihero.dev/ai-coding-dictionary/spec)、または今いる会話を受け取り、issue tracker 上の **[tickets](https://www.aihero.dev/ai-coding-dictionary/ticket)** の集まりに分割します。各チケットは自分の**ブロッキングエッジ**、つまり自分が始められるようになる前に完了しなければならない他のチケットを宣言します。

すべてのチケットは**トレーサーバレット**です: 変更のすべての層（スキーマ、API、UI、テスト）を貫く、細いけれども完全な経路で、入った時点で単独でデモできます。これが、作業を分けるありがちな方法、つまり 1 層ずつ切り出して最後に統合するやり方との違いです。また、各チケットを新しい [context window](https://www.aihero.dev/ai-coding-dictionary/context-window) 1 つに収まる大きさにします。あなたの spec を一度も見たことのない [session](https://www.aihero.dev/ai-coding-dictionary/session) がそのチケットを引き受けるからです。

## この機能を使うタイミング

これは `/to-tickets` と入力して呼び出します。[agent](https://www.aihero.dev/ai-coding-dictionary/agent) が自分から使うことはありません。

| 今いる場所 | 実行するもの |
| --- | --- |
| spec の issue があり、ビルドが複数のセッションにまたがる | `/to-tickets`、または `/to-tickets #<spec_issue>` |
| 計画が会話の中にしかなく、文書にしたことがない | `/to-tickets` はスレッドを直接読むので、spec は不要です |
| 変更全体が 1 つのコンテキストウィンドウに収まる | [implement](https://aihero.dev/skills-implement)。チケットは省きます |
| まだ何も決まっていない | [grill-with-docs](https://aihero.dev/skills-grill-with-docs)、その後 [to-spec](https://aihero.dev/skills-to-spec) |
| [wayfinder](https://aihero.dev/skills-wayfinder) のマップが晴れた | まず [to-spec](https://aihero.dev/skills-to-spec) でマップをまとめ、その後 `/to-tickets` |

`to-tickets` が作ったチケットは、構造上エージェントが着手できる状態になっています。それに対して [triage](https://aihero.dev/skills-triage) を実行しないでください。triage は他の誰かから届いた作業のためのものです。

## 前提条件

`to-tickets` はトラッカーに公開するので、[setup-matt-pocock-skills](https://aihero.dev/skills-setup-matt-pocock-skills) がこのリポジトリのトラッカーを、トリアージラベルの語彙とともに設定している必要があります。どちらの種類でも動きます: GitHub や Linear のような本物のトラッカーでも、追加のセットアップなしで動く `.scratch/` 配下のローカルの Markdown ファイルでもかまいません。

## 層ではなくトレーサーバレット

**横の**スライスは、変更の 1 つの層を出荷します。すべての層が入るまで何も動かず、各チケットの受け入れ条件は別のチケットが担当する作業にまで手を伸ばさなければなりません。**縦の**スライス（トレーサーバレット）は、すべての層を貫く細い経路を一度に出荷するので、単独で検証でき、自分が評価するものすべてを自分で担当します。

これは最もよく破られるルールです。あるチームは、層ごと（corpus、producer、aggregator、selector）に切った 26 チケットの積み重ねを実行し、閉じたチケット 1 つあたり約 20 回のエージェント実行がかかり、その約 4 分の 3 がやり直しでした。そのチーム自身の振り返りは、すべての失敗の種類の原因を、実装ではなく横のスライスにさかのぼっています。

何かを公開する前に、2 つのことが行われます。`to-tickets` は事前のリファクタリング（「変更を簡単にしてから、簡単な変更をする」という原則）を探し、その作業を最初に並べます。次に、分割案を番号付きのリストとして示し、それについてあなたに問いかけます: 粒度は適切か、ブロッキングエッジは本物か、統合や分割すべきものはないか。あなたが承認するまで何もトラッカーには届かず、異議を唱えるのはこの問いかけのときです。

## ブロッキングエッジ

エッジこそが、この成果物の要点です。トラッカーによって 2 通りの働き方をします:

| トラッカー | エッジの置き場所 | 進め方 |
| --- | --- | --- |
| Local markdown | `.scratch/<feature>/issues/<NN>-<slug>.md` 配下の 1 チケット 1 ファイルの中のテキスト。ブロッカーが先になるよう番号付け | 上から下へ、手作業で |
| 本物のトラッカー（GitHub、Linear） | ネイティブのブロッキングリンク、またはトラッカーにあれば sub-issue | ブロッカーが完了したチケットは**フロンティア**に乗り、誰でも着手できる |

どちらの場合も、エッジはチケットの中にあります。トラッカーが決めるのは、それに基づいて何かを並列に動かせるかどうかだけです。`to-tickets` は成果物を作ります。それを実行する（1 セッションずつ、あるいはエージェントの一団で）のは、スキルではなくあなたの仕事です。

## 広範囲のリファクタリングという例外

トレーサーバレットのルールを破る形が 1 つあります。**広範囲のリファクタリング**（wide refactor）とは、**影響範囲**（blast radius）がコードベース全体に及ぶ、1 つの機械的な変更（列の名前を変える、共有のシンボルの型を変えるなど）です。1 つの編集で何千もの呼び出し箇所が壊れるので、どの縦のスライスも green のまま入れることができません。

`to-tickets` は代わりに、それを **expand–contract** として順序付けます:

- **Expand**: 古い形の横に新しい形を追加し、何も壊れないようにする。
- **Migrate**: 影響範囲に応じた大きさ（パッケージごと、ディレクトリごと）のまとまりで呼び出し箇所を移し、まとまりごとに 1 チケットとし、それぞれを expand でブロックする。古い形がまだ存在するので CI は green のまま保たれます。
- **Contract**: 呼び出し側が残っていなくなったら、すべての migrate のまとまりにブロックされたチケットで古い形を削除する。

まとまり単体でも green を保てない場合は、それらが統合ブランチを共有し、すべてが最後の統合と検証のチケットをブロックします。CI が green である必要があるのは、そのチケットのときだけです。

## よくある質問

**3 行の変更に 12 個のチケットを作られました。**
細かく分けすぎることは、このスキルで最も多く報告されている問題で、多くのユーザーが経験しています。[model](https://www.aihero.dev/ai-coding-dictionary/model) はデフォルトで最小単位に分け、それらを意味あるものにするまとまりを失ってしまいます。これを直すのは問いかけのステップです。チケットを統合するよう頼めば、統合してくれます。下限もあります。変更全体が 1 つのコンテキストウィンドウに収まるなら、このスキルはまったく必要ありません。直接 [implement](https://aihero.dev/skills-implement) に進んでください。

**チケットが層ごとに 1 つずつ出てきました: スキーマは全部 1 つに、API は全部別の 1 つに。**
それはまさに縦のスライスのルールが防ごうとしている失敗で、スキルは今でもときどきそれを生みます。問いかけのステップで、チケットごとに 1 つの質問をして見抜いてください: これが終わったら何をデモできるのか？答えのないチケットは横のスライスです。このために各チケットに「デモの経路」の行を加える人もいて、それによってモデルが縦のスライスに向かいやすくなると報告しています。

**GitHub で、チケットが spec の issue の sub-issue として作られませんでした。**
これは十数回の実行と複数のモデルで報告され、[最も詳しくは issue #554](https://github.com/mattpocock/skills/issues/554) にあります。修正済みです: 今の `to-tickets` は各チケットを元の issue の sub-issue にし、GitHub のトラッカーテンプレートがそのコマンド（`gh issue create --parent <n>`、`gh` 2.94 以降）を示しています。古い `docs/agents/issue-tracker.md` を更新するには、[setup-matt-pocock-skills](https://aihero.dev/skills-setup-matt-pocock-skills) を再実行してください。

**本物のブロッキングリンクではなく、issue の本文に「Blocked by」と書かれました。**
これは同じ種類の問題で、[issue #513 で報告されました](https://github.com/mattpocock/skills/issues/513)。そこではエージェントが、GitHub にはネイティブのブロッキング関係がまったくないとまで述べていました。実際にはあります: `gh issue create --blocked-by 12,15`。スキルはブロッカーを先に公開するので、作成時には必ずその番号が使えます。本文のテキストは、ネイティブのエッジがないトラッカーのための代替手段であって、デフォルトではありません。今のチケットテンプレートは、エッジがネイティブのときは `## Blocked by` を省略します。

**ローカルのチケットはどこに置かれますか？v1.1 のノートにはルートレベルの `tickets.md` とありました。**
そう書かれていましたが、それはバグでした。1 つの共有ファイルは、並列のエージェントが書き込んだときに競合状態も引き起こしました。今のローカルモードは、依存の順に、`.scratch/<feature-slug>/issues/<NN>-<slug>.md` 配下に 1 チケット 1 ファイルを書き、ローカルのトラッカーテンプレートがすでに説明していた配置に合わせています。`NN` の接頭辞は本物のチケット ID なので、長いタイトルを打ち直さなくても `/implement 03` で動きます。

**spec を読もうとするたびに途中で切れ続けました。**
非常に大きな spec は、トラッカーの issue がきれいに返せる量を超えてしまうことがあります。頼れるローカルのコピーがないので、エージェントは [tool calls](https://www.aihero.dev/ai-coding-dictionary/tool-call) を使って断片を取得し直し続け、最後までたどり着けません。`/to-spec` と `/to-tickets` の間で [clear](https://www.aihero.dev/ai-coding-dictionary/clearing) や [compact](https://www.aihero.dev/ai-coding-dictionary/compaction) をしないでください。同じコンテキストウィンドウで実行すれば、エージェントが spec を取得し直す必要は一切ありません。

**受け入れ条件が何も評価していませんでした: 作業前から通っているものもありました。**
テンプレートは条件を求めますが、それが失敗しうるかどうかについては何も言わないので、こういうことが起きます。繰り返し現れる形が 3 つあります: ベースのコミットの時点ですでに真である条件、別のチケットの作業でしか満たせない条件、成果物から導くのではなく依頼を言い直しただけの条件です。縦のスライスでほとんどは防げます。新しい振る舞いを届けるスライスは、構造上、ベースのコミットでは失敗するからです。それでも手で確認する価値はあります。各条件について、それが偽であることを示す観察を挙げ、実装者が開始するコミットでそれが失敗することを確認してください。

**チケットは公開されました。実際にはどう実行すればいいですか？**
スキルは成果物の段階で止まり、自動で割り振るモードはありません。割り振りは手作業です: ボードを見て、未完了のブロッカーがないチケットを数え、その数だけエージェントのセッションを開きます。各チケットには新しいコンテキストを与え、チケットの間でクリアしてください。[implement](https://aihero.dev/skills-implement) は、GitHub でもローカルの Markdown でも、終わったときにチケットを確実に閉じたりチェックしたりはしないので、チケットの状態は自分で更新してください。

## 正常に機能している場合

- すべてのチケットに「これが終わったら何をデモできるか？」への答えがあり、その答えが層ではなく振る舞いになっている。
- 何かが公開される前に、それぞれに「Blocked by」の行が付いた番号付きのリストが返ってくる。
- 一番上のチケットにはブロッカーがなく、すぐに始められる。
- チケットの本文に、プロトタイプが生んだスニペットを除いて、ファイルパスや行番号が含まれていない。
- 各チケットが、あなたがその場にいなくても新しいセッションが完了できるもののように読める。
- 事前のリファクタリングが見つかった場合、それが機能のチケットに混ざるのではなく、順序の先頭にある。

## この機能の位置付け

`to-tickets` はメインのビルドチェーンのステップです:

```txt
grill-with-docs → to-spec → to-tickets → implement → code-review → retro
```

上流は [to-spec](https://aihero.dev/skills-to-spec) で、切り分けの元となる確定した spec を渡してくれます。両方を 1 つのコンテキストウィンドウに保ち、間でクリアしないでください。下流は [implement](https://aihero.dev/skills-implement) で、新しいセッションごとに 1 チケットを構築し、テストのために [tdd](https://aihero.dev/skills-tdd) を駆動し、[code-review](https://aihero.dev/skills-code-review) で締めくくります。もう 1 つの下り道が [implement-spec](https://aihero.dev/skills-implement-spec) です。同じブロッキングエッジをタスクグラフとして読み、着手可能なすべてのチケットを 1 つの統合ブランチ上で並列に構築します。どのスキルやフローが合うか分からないときは、[ask-matt](https://aihero.dev/skills-ask-matt) が案内します。
