## 機能

`to-tickets` は、計画、仕様、あるいは現在の会話を **チケット** の集合へ分割し、それらを設定済みの課題（issue）管理システムへ公開します。各チケットはトレーサーバレット形式の垂直スライスであり、さらに自分をブロックしているチケットを明示します。

すべてのチケットは **トレーサーバレット** です。つまり、スキーマ、API、UI、テストなど、すべての統合レイヤーをエンドツーエンドで貫く薄い **垂直スライス** であり、単一レイヤーだけを対象とする水平スライスではありません。完成したスライスはそれ単体でデモまたは検証できるため、エージェントへ安全に割り当てられます。

## この機能を使うタイミング

このスキルは `/to-tickets` と入力して呼び出します。エージェントが自動的に利用することはありません。

合意された計画や仕様が存在し、それをチケットへ分割したい段階で利用してください。会話全体を対象にすることもできますし、仕様書や issue を指定することもできます。その場合、このスキルは本文やコメントを取得してから処理します。まだ変更内容が仕様として文書化されていない場合は、先に仕様を作成してください。そのためには [to-spec](https://aihero.dev/skills-to-spec) を利用します。

## 前提条件

`to-tickets` は課題（issue）管理システムへチケットを公開するため、このリポジトリでは事前に [setup-matt-pocock-skills](https://aihero.dev/skills-setup-matt-pocock-skills) によって課題（issue）管理システムとトリアージ用ラベル体系が設定されている必要があります。実際の課題（issue）管理システムを利用している場合、このスキルは公開時に `ready-for-agent` ラベルを自動で適用します。

## 1つの成果物、2つの読み方

ブロッキング関係（依存関係）こそがこのスキルの本質です。同じチケット群でも、利用する媒体によって2通りの見方ができます。

- **ローカルファイル** → `.scratch/<feature>/issues/` 配下にチケットごとのファイルを作成します。ブロッカーを先に処理できるよう番号が振られ、依存関係はテキストとして記録されます。ユーザー自身が上から順に処理します。
- **実際の課題（issue）管理システム（GitHub、Linear など）** → チケットごとに issue を作成し、依存関係はネイティブなブロックリンク（またはサブ issue）として表現されます。ブロッカーがすべて完了したチケットは **フロンティア** に入り、誰でも着手できます。そのため複数のエージェントが並列で作業できます。

依存関係そのものは媒体に関係なくチケット内に存在します。違いは、それを使って並列実行する仕組みがあるかどうかだけです。`to-tickets` は成果物を作成しますが、それをどのように実行するか（手動で順番に処理するか、並列エージェント群で実行するか）はユーザー次第です。

## 水平スライスではなく垂直スライス

このスキルは1つの重要な区別に基づいています。

**水平スライス** は変更の1レイヤーのみを提供します。たとえばスキーマだけ、あるいは API だけを実装します。そのため、すべてのレイヤーが完成するまで何も動きません。

一方、**垂直スライス**（トレーサーバレット）は、すべてのレイヤーを通る1本の細い経路を同時に提供します。そのため、完成した瞬間からデモ可能になります。

チケット分割の前に、`to-tickets` はまずプレファクタリングの機会を探します。つまり「変更を簡単にしてから、その簡単な変更を行う」という考え方です。その作業を先に配置し、その後チケットの粒度、依存関係、統合または分割の必要性について確認を行います。公開時にはブロッカーを先に作成し、各チケットの「Blocked by」が実在するチケットを参照できるようにします。

## 大規模リファクタリングという例外

トレーサーバレットのルールが当てはまらないケースが1つあります。それが **大規模リファクタリング（wide refactor）** です。

これは、単一の機械的な変更（列名の変更や共有シンボルの型変更など）でありながら、その **影響範囲（blast radius）** がコードベース全体へ広がるものを指します。その結果、1 回の変更で何千もの呼び出し箇所が壊れてしまい、どの垂直スライスもグリーンな状態で着地できなくなります。

`to-tickets` は、このような場合には **expand–contract** パターンで分割します。

- expand: 旧形式を残したまま新形式を追加し、何も壊れない状態を作る。
- migrate: 影響範囲に応じた単位で呼び出し箇所を段階的に移行する。バッチごとに 1 チケットとし、旧形式が存在するため CI は常にグリーンを維持できる。
- contract: 呼び出し元が存在しなくなった時点で旧形式を削除する。

さらに、移行バッチ単体ではグリーンを維持できない場合、それらは共通の統合ブランチを利用し、すべてのチケットが最終的な統合・検証チケットをブロックする形になります。この場合、グリーンであることが保証されるのは最終統合時のみです。

## この機能の位置付け

`to-tickets` は、メイン開発チェーンの一工程です。

```txt
grill-with-docs → to-spec → to-tickets → implement → code-review
```

このスキルは [to-spec](https://aihero.dev/skills-to-spec) と [implement](https://aihero.dev/skills-implement) の間に位置します。`to-spec` はユーザーストーリーを含む確定済みの仕様を提供し、それを元に `to-tickets` が分割を行います。その後 [implement](https://aihero.dev/skills-implement) が各チケットを実装し、内部的に [tdd](https://aihero.dev/skills-tdd) を利用してテストファーストで開発を進めた後、[code-review](https://aihero.dev/skills-code-review) を実行します。

作業はフロンティア上のチケットを、毎回新しいコンテキストで1件ずつ処理してください。チケット間ではコンテキストをクリアすることが推奨されます。どのスキルやフローを利用すべきかわからない場合は、[ask-matt](https://aihero.dev/skills-ask-matt) が案内します。
