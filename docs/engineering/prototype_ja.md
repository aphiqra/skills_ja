## 機能

`prototype` は**疑問に答えるための使い捨てのコード**を書きます: この状態モデルは妥当か、この画面はどう見えるべきか、といった疑問です。疑問が先にあり、それが何を作るかを決めます。間違った疑問に答えるプロトタイプは、どれほど見栄えが良くても無駄です。

使い捨てとは、コードの*書き方*に対する制約であって、破棄する約束ではありません。テストなし、動かすのに必要な分を超えるエラー処理なし、抽象化なし、永続化なし。どれも、学ぼうとしているたった 1 つのことを学ぶ助けにならないからです。残るものは 2 つあります。答えは本番のコードに入り、プロトタイプはその答えの証拠として main から外れたブランチに置かれます。

## この機能を使うタイミング

`/prototype` と入力するか、タスクに合うときに [agent](https://www.aihero.dev/ai-coding-dictionary/agent) が自動的に使います。

話し合いでは決着できない疑問にぶつかった瞬間に使ってください: エッジケースを頭の中に保持しきれない状態機械や、3 つのバージョンを並べて見るまで思い描けない画面などです。こうした疑問では [Grilling](https://www.aihero.dev/ai-coding-dictionary/grilling) のセッションが長くなります。エージェントは言い換え、あなたは推測し、範囲は広がっていきます。グリルをやめ、使い捨て版を作り、それを見て、1 行で答えてください。そうではなく、すでに作ったものがおかしな動きをしていて、その理由を知りたいのなら、[diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs) を使ってください。プロトタイプは何を作るかを探るものであって、作ったものがなぜ壊れているかを探るものではありません。

自分で選ばなくてもここに来ることがあります。[wayfinder](https://aihero.dev/skills-wayfinder) はマップ上に `prototype` の意思決定 [tickets](https://www.aihero.dev/ai-coding-dictionary/ticket) を登録し、あなたはこのスキルでそれに取り組みます。

## 2 つの分岐

疑問が分岐を選び、分岐ごとに異なる成果物ができます:

- **「このロジック / 状態モデルは妥当か？」**: **共有可能な単一の HTML ファイル**。ビルドもサーバーも不要な自己完結した 1 ページで、ダブルクリックで開けます。クリックのたびに描画し直されるラベル付きの状態パネル、モデルを好きな順に試せる自由操作のボタン、そしてタブ切り替えの**ガイド付きウォークスルー**（タブごとに 1 つのシナリオがあり、その下に押すべきボタンが順に並ぶ）があります。すべてがドメインの言葉でラベル付けされているので、デザイナー、PM、ドメインの専門家に渡して、モデルを自分で試してもらえます。ページの背後にあるロジックは、DOM のコードを含まない小さな純粋モジュール（reducer、状態機械、関数の集まり）なので、検証済みのものをそのまま本番のコードに移せます。
- **「これはどう見えるべきか？」**: 1 つのルート上の、**根本的に異なる**複数の UI バリエーション。画面下部に浮かぶバーと URL パラメータ `?variant=` で切り替えられます。バリエーションは色ではなく構造で異なっていなければなりません。少しずつ変えたカードグリッドが 3 つあっても何の答えにもなりません。できる限り、本物のデータと本物の密度を持つ実際のページの中に描画します。空のページで判断したバリエーションは、いつも問題なく見えてしまうからです。

どちらも状態をメモリに持ち、セットアップなしで起動し、ステップごとに状態全体を見せます。どちらかを堅牢にし始めた（テストを足す、本物のデータベースにつなぐ、後で必要になるかもしれないケースのために一般化する）瞬間に、あなたはプロトタイプ作りをやめています。

## プロトタイプは一次情報である

完成したプロトタイプは 2 つのものを残し、それらは別々の場所に行きます。

**答え**（判定と、それが決着させた疑問）は、恒久的な場所に記録します: コミットメッセージ、ADR、実装の issue などです。main には、本番のコードとして答えが残ります。

**プロトタイプ**は答えの出どころである実行可能な証拠であり、削除しません。かといって main に置くものでもありません。誰も保守しないので、すぐに古くなるからです。そこで、main から外れた使い捨ての `prototype/<name>` ブランチにコミットし、決してマージせず、実装の issue にそのブランチへの [context pointer](https://www.aihero.dev/ai-coding-dictionary/context-pointer) を残します。main はきれいなまま保たれ、次に作業を引き継ぐ人はプロトタイプを見つけて再実行できます。

## よくある質問

**え、プロトタイプは削除するはずではなかったのですか？**
もうそうではありません。以前はそうでした: 作って、答えを残して、コードは捨てる。それに対する最も強い反論は速度に関するものではありませんでした。*次の [session](https://www.aihero.dev/ai-coding-dictionary/session) で誰が作業を引き継ぎ、その人は何を手がかりにするのか？*というものでした。プロトタイプを文章で要約すると、それを説得力のあるものにしていた部分が失われます。そこで今のスキルは、プロトタイプを [primary source](https://www.aihero.dev/ai-coding-dictionary/primary-source) として扱います。main から外れた `prototype/<name>` ブランチに置かれ、実装の issue がそこを指します。変わったのはコードの置き場所であって規律ではありません。今でも main にマージされることは決してありません。

**以前はターミナルアプリを作っていました。あれはどこへ行きましたか？**
ロジックの分岐は、今は代わりに共有可能な単一の HTML ファイルを出力します。ターミナルアプリを操作できるのは、リポジトリをクローンしてランタイムをインストールした人だけで、それではプロトタイプが意見を必要とする人たちが除外されてしまいます: デザイナー、PM、状態モデルが何を意味するはずかを知っているドメインの専門家です。ダブルクリックで開き、メールで送った後でも動く自己完結したファイル 1 つなら、誰でも操作できます。その下にある純粋なロジックのモジュールは変わっておらず、今でも本番のコードに移す部分です。

**実装すべきときに、エージェントに `/prototype` を勧められました。**
これは名前に関する既知の問題です。フローを知らないエージェントは、一般的で魅力的な言葉である `prototype` を、チケットができた後の「当然の次のステップ」と読んでしまいます。そのため、設計が会話で決着していても、エージェントはこれを名指しで勧めます。何を作るかがすでに分かっているなら、次のステップはチケットごとの `/implement` です。プロトタイプを使うのは、特定の設計上の疑問が未解決で、話し合っても解決しないときだけにしてください。

**本番の機能を作る前に、アプリケーション全体をプロトタイプにすべきですか（たとえば見込み客へのデモのために）？**
それは、たまたまこのスキルと同じ名前を持つ別の成果物です。ここでいうプロトタイプは 1 つの疑問に絞ったもので、「アプリ全体は何か？」は 1 つの疑問ではありません。アプリ全体のプロトタイプには自然な終わりがないので、本番のアプリへとずるずる変わっていきます: 後片付けは行われず、プロトタイプのルール（テストなし、エラー処理なし）で書かれたコードがユーザーの前に出てしまいます。営業用のデモが必要なら、意図的にデモとして作り、どれも本番用ではないことを明確にしてください。設計上の疑問に決着をつける必要があるなら、その疑問まで絞り込んでください。

**専用のセッションで実行するにはどうすればいいですか？**
プロトタイプは独自のディレクトリに置かれ、疑問を出したスレッドには入れたくない大量の [context](https://www.aihero.dev/ai-coding-dictionary/context) を生み出すので、別の場所で実行し、答えだけを持ち帰ってください。作業をそのセッションに移すのにも、答えを持ち帰るのにも [handoff](https://aihero.dev/skills-handoff) を使います。

**これはトークンを燃やす最速の方法ではありませんか？**
話し合えば答えられた疑問をプロトタイプにしたり、1 つのプロトタイプを機能全体に広げたりすれば、そうなりえます。意味のある比較は、トークンとゼロの比較ではなく、[tokens](https://www.aihero.dev/ai-coding-dictionary/token) と、間違った状態モデルを作って本番の呼び出し側ができた後にそれに気づくこととの比較です。疑問を狭く、実行を短く保てば、消費は釣り合ったものになります。

## 正常に機能している場合

- プロトタイプが何の疑問に答えるために存在するかを 1 文で言え、それが頭の中だけでなく、デモの冒頭に書かれている。
- コードを読まない人でもロジックのデモを操作できる。ファイルを開き、ウォークスルーのタブでボタンを押し、見たものを自分の言葉で説明してくれる。
- 誰かが「待って、それはありえないはず」や「へえ、X だと思い込んでいた」と言う。それは*アイデア*のバグであり、プロトタイプはまさにそのためにあります。
- UI のバリエーションが色や文言だけでなくレイアウトや情報の階層で異なっていて、返ってくるフィードバックが「B のヘッダーと C のサイドバー」のようなものになる。
- 一度の作業で答えが出る。1 日経ってもまだ作っているなら、疑問が大きすぎます。分割してください。
- 終わったとき、main には決定だけがあり、プロトタイプは含まれておらず、実装の issue がまだそれを保持しているブランチを指している。

## この機能の位置付け

`prototype` は**いつでも使えるスタンドアロン**です: 1 つの設計上の疑問に決着をつけるために使い、その後自分の作業に戻ります。別のスキルもこれを実行します。

これを最もよく実行するスキルは [wayfinder](https://aihero.dev/skills-wayfinder) です。wayfinder のマップは**意思決定チケット**でできていて、`prototype` はチケットがなりうる 4 つのタイプの 1 つです: 行く手を阻む疑問が「これはどう見えるべきか」や「どう振る舞うべきか」で、いくら話し合っても解決しないときに使うタイプです。議論が曖昧なとき、wayfinder は反応できる具体的なものを作り、このスキルがそれを作ります。答えがプロトタイプのチケットを解決し、マップはプロトタイプをアセットとしてリンクします。

他の隣人はその上流と下流にいます。[grill-me](https://aihero.dev/skills-grill-me) と [grill-with-docs](https://aihero.dev/skills-grill-with-docs) はグリルで答えられる疑問に答えます。グリルでは答えられない疑問は代わりにここに来て、1 行の答えがインタビューに戻ります。下流では、検証済みの状態モデルや UI の方向性が [to-spec](https://aihero.dev/skills-to-spec) への確定した入力になり、to-spec はプロトタイプが生んだ決定の詰まったスニペットを、文章で説明する代わりにそのまま埋め込めます。それ以外のことは、[ask-matt](https://aihero.dev/skills-ask-matt) がスキル全体を案内します。
