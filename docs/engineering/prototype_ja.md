## 機能

`prototype` は、1 つの設計上の疑問に答えることだけを目的とした、小さく使い捨てのプログラムを作成します。たとえば、この状態モデルは適切か、あるいはこの UI はどのような見た目にすべきか、といった問いに答えるためのものです。

このコードは **最初から使い捨て** であり、そのように明示されます。テストも、実行に必要以上のエラーハンドリングも、抽象化も、永続化もありません。目的は素早く何かを学び、その後で削除することです。そのため、コードを堅牢化し始めた瞬間に、それはもはやプロトタイピングではなくなります。

## この機能を使うタイミング

`/prototype` と入力して呼び出すか、タスク内容が適している場合はエージェントが自動的に利用します。

紙の上だけでは結論を出しにくい設計上の疑問がある場合に利用してください。たとえば、頭の中だけでは把握しきれないケースを持つステートマシンや、複数の案を並べて実際に見比べるまでイメージできない画面などです。一方で、すでに作られたものが正常に動作せず、その原因を調べる必要がある場合は、代わりに [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs) を利用してください。プロトタイピングは何を作るべきかを探るためのものであり、なぜ壊れているのかを調査するためのものではありません。

## 2 つの分岐

問いによってプロトタイプの形が決まり、その形は 2 種類あります。

- **「このロジックや状態モデルは適切だろうか？」** — 小さな対話型ターミナルアプリを作成し、扱いづらいケースに対してステートマシンを動かします。各操作の後に状態全体を表示するため、何が変化したのかを観察できます。
- **「これはどのような見た目にすべきだろうか？」** — 1 つのルートに対して根本的に異なる複数の UI バリエーションを作成し、フローティングバーから切り替えられるようにします。想像ではなく、実際に描画された結果を比較できます。

間違った分岐を選ぶとプロトタイプ全体が無駄になるため、最初に問いを明確にすることが重要です。どちらの分岐でも、状態はメモリ内で管理され、1 つのコマンドで実行でき、各ステップで状態全体を確認できます。

## プロトタイプを一次情報として保持する

完成したプロトタイプは 2 つの成果を残します。1 つは **答え** です。つまり、結論と、それによって解決された問いです。これはコミットメッセージ、ADR、issue などに永続的に記録します。もう 1 つは、**プロトタイプそのものが一次情報源である** という点です。これは、その答えに至る根拠となった実行可能な証拠です。

プロトタイプはメインブランチに置くべきではありません。テストもなく、エラーハンドリングもなく、保守する前提でもないからです。しかし、それは削除すべき理由ではありません。答えが記録された後は、検証済みの判断だけを本番コードへ取り込み、そのプロトタイプ自体は使い捨てブランチへ保存してください。メインブランチには取り込まず、実装用 issue から参照できるようにします。これにより、メインブランチは整理された状態を保ちながら、必要な人はいつでもその実験を再実行できます。メインブランチに放置されたプロトタイプは役目を終えていますが、サイドブランチ上の一次情報として保存されたプロトタイプは役割を維持しています。

## この機能の位置付け

`prototype` は、必要なときにいつでも利用できるスタンドアロン型スキルです。設計上の疑問を解決するために利用し、結論が出たら通常の作業フローへ戻ります。

その結果は次の工程へ引き継がれることがよくあります。検証済みの状態モデルや UI の方向性は、[to-spec](https://aihero.dev/skills-to-spec) が仕様として文書化するための確定した入力になります。また、記録すべきアーキテクチャ上の意思決定であれば、[domain-modeling](https://aihero.dev/skills-domain-modeling) を通じて保存できます。どのスキルやフローを使うべきかわからない場合は、[ask-matt](https://aihero.dev/skills-ask-matt) が案内します。
