## 機能

`resolving-merge-conflicts` は、進行中の git のマージまたはリベースをハンクごとに処理し、その後プロジェクト自身のチェックを実行して、コミットで操作を完了させます。

コンフリクトをテキストの問題として扱うことを拒否します。ハンクに手を付ける前に、それぞれの側をその **[primary source](https://www.aihero.dev/ai-coding-dictionary/primary-source)**（コミットメッセージ、PR、元の issue）までさかのぼるので、2 つのテキストのブロックではなく、2 つの意図の間で選ぶことになり、両立できるところでは両方を残します。両立できないところでは、マージの目的として述べられたものに合う側を選び、そのトレードオフを明示します。衝突を隠すために新しい振る舞いを作り出すことはせず、`--abort` も決して使いません。マージは必ずコミットの完了まで進めます。

## この機能を使うタイミング

`/resolving-merge-conflicts` と入力するか、タスクに合うときに [agent](https://www.aihero.dev/ai-coding-dictionary/agent) が自動的に使います。

git が自力では解決できないコンフリクトで、すでに止まっているときに使います。対象は目の前のコンフリクトだけで、その前後にあるものは含みません:

| あなたの状況 | スキル |
| --- | --- |
| マージやリベースの途中で、ツリーにコンフリクトマーカーがある | これ |
| マージは終わったが、理由の分からないおかしな動きをしている | [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs) |
| ブランチの衝突を減らすための作業の分け方を計画している | どちらでもありません: 下の並列作業についての質問を参照 |

## `ours` や `theirs` より一次情報

このスキルの目的は、フラグによる解決を防ぐことです: `--ours`、`--theirs`、あるいは重要でなさそうなほうのブロックを手で消して、マーカーを消し、ビルドを通すことです。そういう解決は構文的には完璧でも、誰かが意図的に行った変更を黙って捨ててしまうことがあります。

読んでいない意図を残すことはできません。そのため作業は履歴（コミット、PR、[tickets](https://www.aihero.dev/ai-coding-dictionary/ticket)）から始まり、その後でようやく差分に移ります。チェックのステップがあるのも同じ理由です。スキルはリポジトリ自身の [automated checks](https://www.aihero.dev/ai-coding-dictionary/automated-check) を見つけ、コミットの前に実行します。マージは、両方のブランチを満たしながらどちらのテストも通らないコードを生みやすい、git の中で最も危うい場所だからです。

## よくある質問

**Claude Code はすでに自分でかなりうまくコンフリクトを解決します。なぜスキルが必要なのですか？**

付加価値は「一次情報を探す」と「フィードバックループを回す」というステップにあり、それがなければ毎回手でプロンプトに書く必要があります。促されないエージェントは、たいてい差分だけからもっともらしい解決を作り、そこで止まります。このスキルの価値は、エージェントに飛ばさせない 2 つのステップにあります: それぞれの側がなぜ存在するかを読むことと、その後でチェックを実行することです。良い [model](https://www.aihero.dev/ai-coding-dictionary/model) と比べれば小さな上積みですが、それは意図どおりです。少なくとも 1 人の読者は、モデルが良くなるにつれて、これは丸ごと何もしないスキルになると予測しています。

**そもそもコンフリクトを避けるために、並列のエージェントには同じファイルを触らせないようにすべきですか？**

たいていは不要です。並列のタスクの間でファイルを区切るのは、得られるものより失うもののほうが大きいです。エージェントはマージのコンフリクトの扱いが十分上手なので、そのトレードオフは見た目ほど厳しくありません。守る価値のある規律は 1 つだけで、大きなリファクタリングを先に済ませることです。10 本のブランチが分岐した後に大きな名前変更が入るケースは、ずっと高くつきます。

並列の worktree についてのユーザーの報告から、注意点が 1 つあります: 兄弟の [sessions](https://www.aihero.dev/ai-coding-dictionary/session) がそれぞれ自分のツリーでチケットを作る場合、マージで戻すのは、変更を書いたセッションに任せるのが一番です。意図をすでに知っているのはそのセッションだからです。最後に 1 つのエージェントが全員のコンフリクトを解決すると、[context](https://www.aihero.dev/ai-coding-dictionary/context) が失われ、このスキルのステップ 2 でそれを組み立て直す必要が出てきます。

**なぜ決して `--abort` しないのですか？**

中止すると解決の作業が捨てられ、次に試すときには同じコンフリクトにまったくそのまま戻ってきてしまいます。このスキルは、マージが行われることになっている場合のために書かれています。マージすべきでないと決めたのなら、それはループの中の分岐ではなく、呼び出す前に下すべき判断です。

## 正常に機能している場合

- 解決している間、エージェントが差分のハンクだけでなく、コミットメッセージ、PR、issue を引用して示してくる。
- すべてのハンクが、両方の側の振る舞いを保つか、何を捨てたのかとその理由を明記したメモで終わっている。
- どちらのブランチにもなかったものが結果に現れていない。
- エージェントが型チェック、テスト、フォーマットを見つけ、あなたが何か壊れていると気づいた後ではなく、コミットの*前に*実行して green にしている。
- 複数コミットのリベースなら残りのすべてのコミットも含めて操作が完了し、きれいなツリーで終わる。

## この機能の位置付け

他のどのスキルにも依存しない、いつでも使えるスタンドアロンです: git が止まったときに始まり、ツリーがきれいになってコミットされたときに終わります。本当の意味での隣人は [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs) だけで、マージはきれいに解決したのにマージ後のコードがおかしな動きをする時点から引き継ぎます: それはコンフリクトではなく診断の問題です。アイデアから出荷までのメインフローの外にあるので、この前後に何を実行するかについては [ask-matt](https://aihero.dev/skills-ask-matt) が地図になります。
