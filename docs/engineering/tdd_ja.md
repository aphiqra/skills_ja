## 機能

`tdd` は、機能の構築やバグの修正をテストファーストで行います: 失敗するテストを 1 つ書き、それを通すのに必要なだけのコードを書き、次の振る舞いに進みます。そのループが残す価値のあるテストを生むための基準も持っています: 良いテストとは何か、テストをどこに置くか、モックは何のためにあるか、そしてテストスイートを無価値にする 3 つのアンチパターンです。

あなたが先に合意していない seam には、テストを書きません。テストが 1 つも存在しないうちに、テストしようとしている公開の境界を名指しし、あなたの確認を待って止まります。テストにかけられる労力には限りがあり、このステップによって、それをあらゆるエッジケースではなく重要な経路に使えます。`tdd` はまた、ドライバーではなく**リファレンス**です。ループのルールを持っているだけで、それを適用する [session](https://www.aihero.dev/ai-coding-dictionary/session) を進めるのは別の誰か（あなたか [implement](https://aihero.dev/skills-implement)）です。

## この機能を使うタイミング

`/tdd` と入力するか、タスクに合うとき（機能の構築やバグの修正をテストファーストで行うとき、または「red-green-refactor」と言ったとき）に [agent](https://www.aihero.dev/ai-coding-dictionary/agent) が自動的に使います。

入力と観察できる出力を持つ具体的な振る舞いを作ることになっていて、リファクタリングに耐えるテストが欲しいときに使います。

| あなたの状況 | 行き先 |
| --- | --- |
| 入力と出力が定まった振る舞い（ビジネスロジック、リクエスト/レスポンスの契約、変換、バリデーション） | `tdd` |
| 振る舞いがまだ固まっていない | [to-spec](https://aihero.dev/skills-to-spec)。コードを書く前にテストの seam も合意します |
| 問題が本当はテストではなく interface の形にある | [codebase-design](https://aihero.dev/skills-codebase-design) |
| [spec](https://www.aihero.dev/ai-coding-dictionary/spec) や [tickets](https://www.aihero.dev/ai-coding-dictionary/ticket) があり、ビルド全体を任せたい | [implement](https://aihero.dev/skills-implement)。チケットごとに `tdd` を駆動します |
| 設定、配線、つなぎのコード、型注釈、単純な CRUD の委譲 | ここにはぴったり合うものがありません。下の未解決の不足を参照 |

最後の行は本物の不足です。スキルは seam を*どこに*置くかは決めますが、変更がそもそもループに値する*かどうか*を決めるものは何もありません。アサートの基準となる独立した正解の情報源がない変更にこれを実行すると、実装を言い直しただけのテストができます。スキルが警告している自己言及的（tautological）なアンチパターンに、反対側から行き着いてしまうのです。これは [issue #746](https://github.com/mattpocock/skills/issues/746) で、未解決です。それが閉じられるまでは、その判断は自分で下すか、`CLAUDE.md` にルールを書いておいてください。

## 前提条件

[codebase-design](https://aihero.dev/skills-codebase-design) がインストールされている必要があります。`tdd` はかつて deep module と interface の設計についての独自のメモを持っていましたが、v1.0 で共通のスキルに任せるために削除され、今の `tdd` はその interface 設計の語彙を使います。それ以外に必要なものはありません。スキルは [stateless](https://www.aihero.dev/ai-coding-dictionary/stateless) で、独自のファイルを書くこともありません。

## ループと、それを回す seam

このスキルは 3 つの用語に基づいています。

**Red-green。** 失敗するテストを書き、それを通すのに必要なだけのコードを書きます。次の次のテストのためのコードは書きません。リファクタリングのフェーズはありません。エージェントがほとんど実行しなかったこと、そしてレビューと実装は別々のセッションにしたほうがうまくいくことから、スキルは 2026 年 6 月にそれを取り除きました。リファクタリングは [code-review](https://aihero.dev/skills-code-review) の担当です。

**Vertical slice（縦のスライス）。** 1 つの seam で 1 つのテストを書き、最小限の実装をし、繰り返します。最初のサイクルは、1 本の経路を端から端まで証明する**トレーサーバレット**です。その反対が横のスライスです: 先にすべてのテスト、その後ですべてのコード。まとめて書かれたテストは*想像上の*振る舞いを検証します。ユーザーがすることではなく物の形を確認し、実装を理解する前にテストの構造を固定してしまいます。

**事前に合意した seam。** seam とは、内部に手を入れずに振る舞いを観察できる公開の境界です。このルールに例外はありません。確認されていない seam にはテストを置きません。チェーン全体では、seam はもっと前、[to-spec](https://aihero.dev/skills-to-spec) の間に合意されます: 「`/tdd` は事前に合意したテストの seam でだけ作業するよう指示され、`/code-review` は合意済みのテストの seam だけが使われたことを確認する。」単独で呼び出された場合、`tdd` はあなたに直接尋ねます。

防ぐために書かれている 3 つのアンチパターン:

| アンチパターン | 見分け方 |
| --- | --- |
| Implementation-coupled（実装への密結合） | 振る舞いは変わっていないのに、内部の関数の名前を変えるとテストが壊れる。内部の協力オブジェクトのモック、呼び出し回数のアサート、interface の代わりにデータベースへのクエリで検証すること。 |
| Tautological（自己言及的） | 期待値がコードと同じ方法で計算されているので、テストは構造上必ず通る。期待値は別のところから持ってくる必要があります: 既知の正しいリテラル、検証済みの例、spec など。 |
| Horizontal slicing（横のスライス） | 実装が 1 つもないうちに、テストがまとめて入っている。 |

モックはシステムの境界のためだけのものです: 外部の API、時刻、乱数、場合によってはファイルシステムやデータベース。自分のモジュールは決してモックしないでください。

## よくある質問

**なぜリファクタリングしないのですか？説明には「red-green-refactor」と書いてあります。**

リファクタリングのステップは削除されたのに、説明は削除されなかったからです。削除は意図的なものでした。エージェントはそのステップをほとんど実行せず、実装とレビューを別々のセッションにしておくほうがうまくいきます。結果が教科書どおりの TDD と呼べるかどうかより、ループがより良いコードを生むかどうかのほうが重要です。起動のフレーズと本文の食い違いは [issue #589](https://github.com/mattpocock/skills/issues/589) として登録され、まだ未解決なので、「red-green-refactor」は今もスキルを起動するフレーズとして機能します。得られるのはレッド・グリーンで、リファクタリングは [code-review](https://aihero.dev/skills-code-review) で行われます。

**テストの seam を選ぶよう言われましたが、どれを選べばいいか分かりませんでした。**

これはこのスキルで最も多く報告されている摩擦です（[issue #607](https://github.com/mattpocock/skills/issues/607)）。プロンプトは候補の seam を名前だけで並べ、それぞれが何を検出し何を見逃すかについては何も書かないので、ラベルの間で選ぶことになります。修正はまだ出荷されていません。実用的な回避策は、答える前に、エージェントにトレードオフを尋ねることです: コンポーネントレベルの seam は、統合レベルの seam が検出するもののうち何を見逃すのか、そしてどのくらい遅いのか。チェーンが `to-spec` で seam を前もって合意するのもこのためです。そこでは 1 つのプロンプトではなく、機能全体を見渡せます。

**スキルにはまずレッドと書いてあるのに、テストより先に実装を書きました。**

起こります。あるユーザーが [model](https://www.aihero.dev/ai-coding-dictionary/model) を問い詰めたところ、珍しく正直な答えが返ってきました: 「スキルに『一度に 1 つのテストを書き、正しい理由で失敗するのを確認する』と書いてあるのは知っていた。読んだ。ただ、いつもの癖に戻ってしまった。」スキルはこれを受け入れています。エージェントを 100% 従わせる指示はありませんし、言い回しを厳しくすれば、わずかな効果のためにエージェントの創造性を制限してしまいます。エージェントが厳密に従わなくても、全体としてはやはり結果が良くなるので、ループを回す価値はあります。特定のスライスで厳密に守ることが重要なら、スキルが強制してくれると信じるのではなく、実行を見守ってください。

**ブラウザテストや E2E テストを先に書くべきですか？**

たいていは書くべきではありませんが、スキルはそれを止めません。あるユーザーは、エージェントが先に Playwright のテストを書き、その後長いループで再実行を続けた末に、まだ存在しない機能について*テスト*が壊れていると結論づけたと報告しています。ブラウザテストは遅いので、レッド・グリーンのフィードバックループが割に合わなくなります。リポジトリの `CLAUDE.md` に、ブラウザテストは振る舞いが動くようになってから書く、と書いておいてください。

**`/tdd` は `/implement` や、講座の `/do-work` を置き換えるものですか？**

いいえ。`/tdd` は方法論を記述するものです。`/implement` は作業 → フィードバック → コミットという単純なループで、`/do-work` の直接の代わりです。講座の `/do-work` という 1 つのステップは、今は `/implement`、`/tdd`、`/code-review` に分かれています。チケットに対してどれを実行するかを聞いているなら、答えはほぼ必ず `/implement` です。

**deep module と interface 設計のガイダンスはどこへ行きましたか？**

v1.0 で [codebase-design](https://aihero.dev/skills-codebase-design) に移り、複数のスキルが 1 つの語彙を共有できるよう一般化されました。同時に `refactoring.md` もなくなりました。リファクタリングは今は [code-review](https://aihero.dev/skills-code-review) の仕事で、そのスキルが Fowler の smell baseline を持っています。

**他のチケットのことを知っていますか？**

いいえ。1 つのチケットに対して実行すると、issue のグラフの残りの部分が見えないので、兄弟のチケットに属する作業を提案することがあります（[issue #129](https://github.com/mattpocock/skills/issues/129)）。これは `tdd` の仕事ではありません。チケットと一緒に spec を渡すと役に立ちますが、そもそもチケットの大きさを適正にしておくほうがもっと役に立ちます。

## 正常に機能している場合

- テストファイルが 1 つも存在しないうちに、止まってテストしようとしている seam を名指しし、待つ。
- テストがまとめて出てきてからコードがまとめて出てくるのではなく、テストが 1 つ現れ、red になり、通すのに必要なだけのコードが書かれ、その後で初めて次のテストが現れる。
- テストの名前が内部の仕組み（「checkout calls paymentService.process」）ではなく、能力（「user can checkout with valid cart」）として読める。
- アサーションの期待値が、コードと同じ方法で計算し直した値ではなく、spec までたどれるリテラルになっている。
- 内部の関数の名前を変えても、スイートの中で何も壊れない。
- モックが外部の境界（決済 API、時計）にだけ現れ、自分のモジュールの周りには決して現れない。

## この機能の位置付け

`tdd` はメインチェーンのビルドのステップの中で動くもので、それ自体はステップではありません:

```txt
grill-with-docs → to-spec → to-tickets → implement → code-review → retro
```

[to-spec](https://aihero.dev/skills-to-spec) がテストの seam を前もって合意し、[implement](https://aihero.dev/skills-implement) がチケットごとに `tdd` を駆動し、[code-review](https://aihero.dev/skills-code-review) が後で合意した seam だけが使われたことを確認し、`tdd` がもう行わないリファクタリングを担当します。もう 1 つの隣人は [codebase-design](https://aihero.dev/skills-codebase-design) で、`tdd` が使う seam と deep module の語彙の共通の出典です。具体的に作る振る舞いがあり、完全な spec がないときは、いつでも単独で使うこともできます。どのスキルが状況に合うか分からないときは、[ask-matt](https://aihero.dev/skills-ask-matt) が案内します。
