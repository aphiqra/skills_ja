## 機能

`tdd` は、機能の実装やバグ修正をテストファーストで行い、1つの振る舞いずつ、レッド・グリーンループを通じてコードを作り上げていきます。

このスキルは **最初にすべてのテストを書くことはありません**。先にテストをまとめて作成する（「水平スライス」）方法では、_想像上の_ 振る舞いに対するテストが生まれます。そうしたテストは構造だけを確認し、実際の変更に対して鈍感になっていきます。`tdd` は代わりに垂直スライスを採用します。1つのテストを書き、それを通すために必要最小限のコードを書き、その後で次のテストを書くという流れです。各サイクルは前のサイクルで得られた知見に基づいて進みます。テストは公開インターフェースのみを対象とするため、その下の実装は変更できてもテストを変更する必要はありません。

## この機能を使うタイミング

`/tdd` と入力するか、タスク内容が適している場合はエージェントが自動的に利用します。たとえば、テストファーストで機能を実装する場合、バグを修正する場合、あるいは「red-green-refactor」と指示した場合です。

具体的な振る舞いが定義されており、リファクタリング後も維持できるテストを作成したい場合に利用してください。まだ振る舞いが明確になっていない場合は、先に仕様を確定してください。そのためには [to-spec](https://aihero.dev/skills-to-spec) を利用します。作業の本質がテストではなくインターフェースの形にある場合は、[codebase-design](https://aihero.dev/skills-codebase-design) を利用してください。`tdd` は計画段階で、深いモジュールに関する語彙を利用するためにそこを参照します。

## レッド・グリーンを1スライスずつ進める

中心となる考え方は **レッド・グリーンループ** です。まず失敗するテストを書き（レッド）、それを通すために必要最小限のコードを書き（グリーン）、その後で次の振る舞いに対して同じことを繰り返します。各サイクルは前回学んだ内容を反映して進みます。最初のサイクルは **トレーサーバレット** です。つまり、機能を広げていく前に、1つの経路がエンドツーエンドで動作することを証明するためのテストです。コードを書いた直後であるため、何が重要な振る舞いで、どのように検証すべきかを正確に把握できます。そのため、まだ理解していないテスト構造へ先走ってコミットすることはありません。

テストの健全性を保つためのルールは2つあります。優れたテストは仕様書のように読めること（「有効なカートでユーザーがチェックアウトできる」など）、そして公開 API を通る実際のコードパスを検証することです。そのため、内部関数名を変更してもテストは壊れません。また、期待値は独立した正解ソースから取得する必要があります。たとえば、既知の正しいリテラル値、具体例、仕様書などです。コードと同じ方法で期待値を再計算してはいけません。そのような **自己循環的（tautological）** なテストは構造上必ず成功してしまい、何の保証も与えないからです。

リファクタリングはテストスイートがグリーンになってからのみ行います。レッドの状態では行いません。

## 正常に機能している場合

- 1つのテストを書き、それを通してから次のテストを書くこと。テストをまとめて書いた後でコードをまとめて書くことはしないこと。
- テストが内部実装ではなく振る舞いを表現しており、内部名称の変更に耐えられること。
- 期待値が仕様書に基づくリテラル値であり、コードと同じ方法で導出された値ではないこと。

## この機能の位置付け

`tdd` は、メイン開発チェーンがコードを書く際に使用するレッド・グリーンループです。

```txt
grill-with-docs → to-spec → to-tickets → implement → code-review
```

[implement](https://aihero.dev/skills-implement) はこのチェーンの実装工程であり、各チケットをテストファーストで実装するために内部的に `tdd` を利用し、その後 [code-review](https://aihero.dev/skills-code-review) へ引き渡します。そのため `tdd` は独立した工程ではなく、その内部エンジンです。

また、完全な仕様が存在しなくても、具体的な振る舞いを実装したい場合には直接利用できます。もう1つの関連スキルは [codebase-design](https://aihero.dev/skills-codebase-design) であり、`tdd` はそこで定義される深いモジュールの境界（seam）を見つけ、それをテスト対象として活用します。どのスキルやフローを利用すべきかわからない場合は、[ask-matt](https://aihero.dev/skills-ask-matt) が案内します。
