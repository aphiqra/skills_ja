## 機能

`domain-modeling` は、設計を進めている最中に、プロジェクトの**ユビキタス言語**を構築し、洗練させます。用語集と食い違う用語に異議を唱え、曖昧な言葉を使ったところでは正確な言葉を求め、関係性を具体的なシナリオで検証して、境界が厳密になるまで続けます。

これは受け身ではなく**能動的な**規律です。`GLOSSARY.md` を読んで語彙を借りることは、どのスキルにもできます。このスキルはモデルを*変更する*ときのためのものなので、あなたの話をさえぎります。整った用語集を最後にまとめて作るのではなく、会話の途中で用語が決まった瞬間に、それを `GLOSSARY.md` に書き込みます。最後に書く用語集は [session](https://www.aihero.dev/ai-coding-dictionary/session) の要約であり、その場で書くものはセッションの成果そのものです。

## この機能を使うタイミング

`/domain-modeling` と入力するか、タスクに合うときにエージェントが自動的に使います。実際には、自動での呼び出しはこのスキルの最も弱い部分です。`grill-with-docs` や `wayfinder` がこれを読み込むよう指示しても、[models](https://www.aihero.dev/ai-coding-dictionary/model) は `grilling` を読み込んでこちらを飛ばすことがよくあります。[grilling](https://www.aihero.dev/ai-coding-dictionary/grilling) のセッションが終わっても `GLOSSARY.md` が変わっていなければ、それが起きたということです。もう一方のスキルと一緒に、名前を指定して呼び出してください。

*言葉*が問題のときに使います:

| 状況 | 対処 |
| --- | --- |
| 2 人が「cancellation」で別のことを指している | `domain-modeling`: 正規の用語を選び、もう一方を `_Avoid_` に挙げる |
| 「Account」が 3 つのファイルで 3 つの役割を担っている | `domain-modeling`: Customer と User に分ける |
| 元に戻しにくいアーキテクチャ上の選択をしたところ | `domain-modeling`: その選択が基準を満たせば、ADR を提案する |
| モジュールの*形*が問題: seam をどこに置くか、interface をどれだけ深くするか | [codebase-design](https://aihero.dev/skills-codebase-design) |
| 作る前に計画全体を問い詰めてほしい | [grill-with-docs](https://aihero.dev/skills-grill-with-docs)。その下でこのスキルを駆動します |
| 用語を変えるのではなく、調べたいだけ | 何も要りません。`GLOSSARY.md` を読んでください。ただのファイルです。 |

## 前提条件

事前に必要なものはありません。スキルは 2 か所に書き込み、どちらも必要になった時点で作成します:

- リポジトリのルートにある **`GLOSSARY.md`**。最初の用語が決まったときに作成します。ルートに `GLOSSARY-MAP.md` があるリポジトリでは、用語はそのマップが指す各コンテキストの `GLOSSARY.md` に入ります。
- **`docs/adr/`**。基準を満たす最初の ADR とともに作成します。

始める前に何かが存在している必要はなく、スキルが前もって何かを作ることもありません。

## 2 つの成果物、2 つの基準

用語集と ADR には異なる基準があります。このスキルで起きる問題のほとんどは、両者を混同することから生じます。

| | `GLOSSARY.md` | `docs/adr/NNNN-slug.md` |
| --- | --- | --- |
| 保持するもの | 用語。ある物が何で**ある**かを 1〜2 文で書き、採用しなかった同義語を `_Avoid_` に挙げる | 1 つの決定を 1〜3 文で: 背景、選択、理由 |
| 書く基準 | 曖昧だった用語が正規のものになった | **3 つすべて**: 元に戻しにくい、背景を知らないと意外に思える、本物のトレードオフの結果である |
| 書くタイミング | 用語が決まった瞬間に、その場で | 前提とせず、提案する |
| 決して保持しないもの | 実装の詳細、[spec](https://www.aihero.dev/ai-coding-dictionary/spec)、メモ書き、一般的なプログラミングの概念 | このセッションで行ったすべての選択の日記 |

ADR の 3 つのテストのどれか 1 つでも満たさなければ、ADR は書きません。簡単に元に戻せる決定はそのうち元に戻されるだけです。意外でない決定は誰の疑問にもなりません。本当の代替案がない決定は、当たり前のことをしたと記録するだけです。

最も重要なのは `GLOSSARY.md` のルールです。実際に破られるのがこのルールだからです。**それは用語集であり、それ以外の何物でもありません。**放っておくと、モデルは「`GLOSSARY.md` に書く」を、あなたの答えをすべて保存してよいという許可と受け取り、ファイルは書きかけの spec になってしまいます。これはこのスキルで最も多く報告されている問題で、複数のモデルで起きています。

## 相互参照と、その限界

あなたが何かの仕組みを述べると、スキルはコードを確認し、矛盾があれば指摘します。*「あなたのコードは Order 全体をキャンセルしていますが、今、部分的なキャンセルが可能だと言いました。どちらが正しいですか？」*スキルは、言葉とコードのどちらかを変える前に、両者を声に出して一致させます。

相互参照するのは**コード**と、コミット済みの `GLOSSARY.md` と ADR だけで、それ以外は見ません。issue tracker は検索しません。チームが名前の衝突について議論し、何か月も前にクローズ済みの issue で決着をつけていても、スキルはそれを新しい問題であるかのように再び持ち出します。これを直す [未解決の要望](https://github.com/mattpocock/skills/issues/717) があります。それまでの回避策は、スキルがすでに読んでいる自分の `docs/agents/domain.md` にその指示を書いておくことです。

## よくある質問

**`GLOSSARY.md` が 500 行、1,000 行、3,000 行になりました。どうすればいいですか？**
大きさは症状です。原因は、用語集に入るべきでなかった実装の詳細や決定をファイルが取り込んでしまったことです。直す方法は直接の指示です: `/grill-with-docs make my GLOSSARY.md more concise and remove any implementation details from it`。肥大化したファイルに対して実行すると、ほとんどが消えます。`GLOSSARY-MAP.md` で分割するのは、ファイルが引き締まった後でも、読む人が一度に抱えたくない 2 つのドメインを含んでいる場合だけにしてください。肥大化したファイルを分割すると、肥大化したファイルが複数できるだけです。そもそも肥大化を防ぐには、このスキルの指示はまだ十分に強くなく、それを追跡する issue はまだ未解決です。

**なぜ `CONTEXT.md` ではなく `GLOSSARY.md` なのですか？**
1.3.0 までは `CONTEXT.md`（と `CONTEXT-MAP.md`）でした。このファイルは用語集であり、それ以外の何物でもないので、`GLOSSARY.md` という名前がそれを表しています。また、ある読者が言うように「AI エージェントにとっては何もかもが [context](https://www.aihero.dev/ai-coding-dictionary/context) だ」からです。リポジトリにまだ `CONTEXT.md` があるなら、`/setup-matt-pocock-skills` を再実行してください: ファイルを `git mv` し、`docs/agents/domain.md` を更新することを提案してくれます。セットのすべてのスキルが `GLOSSARY.md` を探すので、古い名前のままにするには、そのすべてに手を加える必要があります。

**`/ubiquitous-language` はどこへ行きましたか？**
非推奨ではなく、削除されました。その役割は `domain-modeling` に移り、1 回の会話から用語集を吐き出すのではなく、モデル全体を継続的に保守するようになりました。語彙の徹底は、重要性が下がったのではなく、むしろ上がっています。覚えておいて別途実行するものではなく、グリル、トリアージ、マップ作りの下で動くようになったのです。

**用語集がまったくないコードベースで、どうやって用語集を作ればいいですか？**
自然にたまるのを待つのではなく、はっきり頼んでください。文書化されている方法は `/grill-with-docs help me scaffold my existing repo with a GLOSSARY.md` です。長い質問攻めを覚悟してください。あるユーザーは、ファイルが形になるまでに 50 を超える質問があったと報告しています。既存のリポジトリでは、ついでに使うだけでは用語集の構築があまりに遅すぎます。

**ドメインモデルはそのままにして、独自の ADR 形式を使えますか？**
今のところ、すっきりとはできません。用語集の部分と ADR の部分は 1 つのスキルで配布されているので、確立した ADR の規約（別のテンプレート、別の場所、別の命名）を持つチームには、自分たちの流儀と食い違う指示が届きます。現時点の選択肢は、スキルをローカルにコピーして編集するか、リポジトリ自身のエージェント向け文書で ADR の規約を上書きすることです。両者を分けることは [未解決の要望](https://github.com/mattpocock/skills/issues/557) になっています。

**用語集は本当に手間に見合いますか？レビューする成果物が 1 つ増えるうえ、古くなることもあります。**
見合わないこともあります。DDD は実装に近づくほど役に立たなくなります。効果があるのは上流、つまり命名と概念のすり合わせであって、集約や層の形式張った作法ではありません。同義語の管理が重要なのは命名の境界です: モジュール名、テーブル名、ステータスの enum、issue のタイトル、CLI コマンドなど。普通の文章ではずっと重要度が下がります。ドメイン用語は、それをすでに共有している*人間同士*のコミュニケーションを圧縮するものであって、エージェントは平易な英語の説明にも同じように反応する、という反論もあります。その見方に立てば、用語集の価値はエージェントを良くすることではなく、あなたやレビュアーとエージェントのしていることとの認識を合わせておくことにあります。1 日で終わるビルドなら省いてください。そして、レビューされていない、エージェントが書いた用語集は、ないより悪いものです: 後のセッションが真実として扱う、自信たっぷりの主張で埋まってしまいます。

**曖昧なプロンプトを、代わりにドメインの言葉に変えてくれますか？**
いいえ。そういうスキルの予定もありません。自分で理解していないドメインの言葉は、書き留めた瞬間に意味を失います。このスキルは、あなたが理解を持った後でその正確さを徹底させるものであって、あなたが持っていない語彙を作り出すものではありません。関連する落とし穴は、モデリングをせずにドメインの言葉を使うことです。間違った概念の上に正しい名詞を載せると、正しく読めるのに正しくない出力ができあがります。

## 正常に機能している場合

- 1 つを選んで先に進む代わりに、2 つのうちどちらのことを言ったのか、話の途中で止めて尋ねてくる。
- `GLOSSARY.md` が最後にまとめてではなく、会話の**最中に**変わる。
- 明日元に戻せるようなことについては ADR を書くのを断り、3 つのテストのどれを満たさなかったかを伝える。
- 新しい項目が、ある物が何で*ある*かを 1〜2 文で定義し、手放す言葉を `_Avoid_` に挙げている。
- コードとあなたの発言が食い違うときに、あなたのコードを引用して返してくる。
- `GLOSSARY.md` が長くなるのと同じくらい、短くもなる。

## この機能の位置付け

`domain-modeling` は**モデル起動型のリファレンス**で、単独で動くよりも、他のスキルの*下で*動くことのほうが多いです。[grill-with-docs](https://aihero.dev/skills-grill-with-docs) はグリルのセッションを通じてこれを駆動し、[wayfinder](https://aihero.dev/skills-wayfinder) はマップを描く間これを読み込み、[triage](https://aihero.dev/skills-triage) は [tickets](https://www.aihero.dev/ai-coding-dictionary/ticket) をプロジェクト自身の言葉で保つためにこれを使い、[improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) は決定が固まるにつれてこれを呼び出します。最も近い兄弟は [codebase-design](https://aihero.dev/skills-codebase-design) です。両者は他のすべての下にある語彙レイヤーで、こちらは*ドメイン*を、あちらはモジュールの*形*を担当します。普段これを読み込むスキルの手順に乗らずに、規律だけを使いたいときは、直接呼び出すこともできます。どのスキルが合うか分からないときは、[ask-matt](https://aihero.dev/skills-ask-matt) が案内します。
