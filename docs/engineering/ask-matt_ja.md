## 機能

`ask-matt` は、このリポジトリのスキルを案内するルーターです。あなたが今いる状況（どこから始めればいいか分からないアイデア、次々に届くバグ報告、長くなりすぎた [session](https://www.aihero.dev/ai-coding-dictionary/session) など）を説明すると、それに合うスキル、またはスキルの順序を示し、その中で人間が判断する箇所がどこかも教えてくれます。

推奨したら、そこで止まります。グリルも、[spec](https://www.aihero.dev/ai-coding-dictionary/spec) の作成も、ファイルを開くことも、名前を挙げたスキルを実行することもしません。返ってくるのは次に入力すべきものであり、入力するのはあなたです。また、これはこのリポジトリのスキルを手書きでまとめた地図であって、インストール済みのものをスキャンするわけではないので、あなた自身のスキルや他の作者のスキルへは案内しません。

## この機能を使うタイミング

これは `/ask-matt` と入力して呼び出します。エージェントが自分から使うことはありません。

| あなたの状況 | ルーターが返すもの |
| --- | --- |
| アイデアはあるが、どこから始めればいいか分からない | メインフローの先頭と、spec を省けるほどビルドが小さいかどうか |
| 他の人からバグや依頼が届いている | [triage](https://aihero.dev/skills-triage) のオンランプと、自分で作った [tickets](https://www.aihero.dev/ai-coding-dictionary/ticket) がそこに乗るべきでない理由 |
| 入れ替え可能に見える 2 つのスキル | 両者の境界線。たいていは好みの問題ではなく、具体的なテスト 1 つで決まります。[grill-me](https://aihero.dev/skills-grill-me) か [grill-with-docs](https://aihero.dev/skills-grill-with-docs) かは作業ディレクトリにいるかどうかで決まり、[grill-with-docs](https://aihero.dev/skills-grill-with-docs) か [wayfinder](https://aihero.dev/skills-wayfinder) かは取り組みが 1 セッションに収まるかどうかで決まります |
| 長いセッションと、[context](https://www.aihero.dev/ai-coding-dictionary/context) についての判断 | フェーズの境界での 5 つの選択肢に対する、順序付きの判断ツリー |
| すでに選んであるスキル | 役に立つものはありません。そのスキルを直接呼び出してください。 |

## 前提条件

ルーターはスキルの名前を挙げるだけで、インストールはしません。推奨を実行に移すには、示されたスキルがすべてインストールされている必要があり、ルーターが知っているのはこのリポジトリの promoted スキルだけです。

トラッカーに依存するルート（triage、`to-spec`、`to-tickets`、`implement`）は、[setup-matt-pocock-skills](https://aihero.dev/skills-setup-matt-pocock-skills) がすでにリポジトリに issue tracker を設定していることを前提にしています。ルーターは、その設定が済む前でもこれらを推奨します。

## スキルではなくフロー

このスキルのキーワードは **flow** です。単一のスキルではなく、スキルを*通る*経路のことです。あなたが状況を伝えると、ルーターはあなたをフロー上のあるステップに置きます。これは「キーワードに一致するスキルはこれです」とは違う答えです。ルートには 5 種類あり、スキル本体がそれらを詳しく説明しています:

- **メインフロー**: アイデアから出荷まで。グリル、spec、tickets、実装（チケットを 1 つずつ、または [implement-spec](https://aihero.dev/skills-implement-spec) でタスクグラフ全体を並列に）、レビュー、そして [retro](https://aihero.dev/skills-retro) です。retro は、ビルドから学んだことをエージェントの環境に反映します。分岐は 2 つあります。1 つはプロトタイプへの迂回で、質問を決着させるのに実行可能なコードが必要なときに使います。もう 1 つは spec と tickets への分割で、ビルドが複数のセッションにまたがるときにだけ、そのコストに見合います。
- **オンランプ**: 作業を生み出し、その後メインフローに合流する状況です。届いたバグ報告、何かが壊れている状態、または 1 セッションでは扱えないほど見通しが悪く大きな取り組みです。
- **コードベースの健全性**: 機能開発ではなく保守です。[improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) がコードを調べて深いモジュール化の機会を探し、見つかったものはそれぞれアイデアとしてメインフローに戻ります。
- **スタンドアロン**: どのフローにも属さず、単独で使うものです。プロトタイプ、アンケート、調査などです。
- **下層の語彙レイヤー**: プロセスではなく言葉が問題のときに、他のスキルが取り込む 2 つのリファレンスです。

## フェーズの境界

このスキルのもう 1 つの重要な考え方が **phase boundary** です。フェーズとはセッション内の作業のまとまり（[grilling](https://www.aihero.dev/ai-coding-dictionary/grilling)、実装、QA など）であり、2 つのフェーズの境界こそが「このコンテキストをどうするか」という問いを考える唯一の場所です。フェーズの途中では判断することはありません。そのまま続けるか、残りを [subagents](https://www.aihero.dev/ai-coding-dictionary/subagent) に分割するかです。

| 選択肢 | 選ぶべきとき |
| --- | --- |
| **Continue** | 次のフェーズがこのフェーズの内容をそのまま必要としている、または [smart zone](https://www.aihero.dev/ai-coding-dictionary/smart-zone) に余裕があるとき。セッションを [primary source](https://www.aihero.dev/ai-coding-dictionary/primary-source) として保てる唯一の手段なので、最初に除外できるか検討します |
| **`/clear`** | これまでの内容がすべて捨ててよいものであるとき。最も安い選択肢ですが、間違っていても元に戻せません |
| **[handoff](https://aihero.dev/skills-handoff)** | 何かを持ち運ぶ必要があるとき。新しい [harness](https://www.aihero.dev/ai-coding-dictionary/harness)、新しいディレクトリ、同僚、フェーズの途中で分岐させるサイドタスクなど |
| **Subagent** | タスクの範囲が十分に絞られていて、あなたが [キーボードから離れて](https://www.aihero.dev/ai-coding-dictionary/afk) いても実行できるとき |
| **`/compact`** | 上のどれにも当てはまらないとき。これがデフォルトで、判断ツリーはここで終わることが多いです |

このうち 2 つを取り違える人が多いので、ルーターは一覧だけでなく順序も示します。`/handoff` はコンテキストウィンドウ間を移動する汎用の方法に見えますが、そうではありません。得られるのは持ち運びやすさだけです。`/compact` は判断ツリーの最初ではなく最後の選択肢です。その上にある 4 つの選択肢は、いずれもそれより安いか、より的確だからです。

## よくある質問

**スキルを正しい順に並べた一覧はないのですか？**

README にそれを載せてほしいという要望は何度も来ています。このスキルこそがその一覧です。静的な表なら `wayfinder → to-spec → to-tickets → implement → code-review → retro` と書くことになり、ほとんどの状況で間違いになります。大事なのは分岐です: コードベースはあるか、ビルドはセッションをまたぐか、話し合いでこの質問は決着するか。その代わり、ルーターは手作業で保守されているので、リポジトリより遅れます。`/grilling` は、ルーターがその名前を挙げるよりずっと前に出荷されていました。

**スキルの半分がインストールされていないと言われました。**

これは既知のバグで、まだ修正されていません。ルーターが案内するスキルのほとんどは `disable-model-invocation: true` を設定しているため、ハーネスはエージェントのコンテキストに注入するスキル一覧からそれらを除外します。エージェントはその一覧をすべてだと受け取り、それらが見つからないと報告します。報告されたあるセッションでは、spec と tickets のフロー全体が存在しないと判断し、素の `/grilling` と `/tdd` に案内し直しました。plugin の 27 スキルのうち 16 がこのフラグを持っているので、これは例外ではなくよくあるケースです。スキルはインストールされています。かまわずスラッシュコマンドを入力するか、何が入っているかの根拠である `.claude-plugin/plugin.json` を確認してください。

**スキルの動作を説明されたのに、そのスキルはそういう動作をしません。**

これも実際のバグで、やはり修正されていません。ルーターは各スキルそのものではなく、自分が持っている 1 行の要約をもとに答えます。ある詳細な報告では、1 つのセッションで 3 件の事例が追跡されており、その中には「スレッドを spec に変換する」という要約だけを根拠に [to-spec](https://aihero.dev/skills-to-spec) を飛ばすよう勧めたものもありました。ルーターは `to-spec/SKILL.md` を一度も開いていませんでした。どの事例でも、確認したのはユーザーが反論した後だけで、自分から確認することはありませんでした。そこで `to-spec` を飛ばしたことで本来行うはずの seam の確認が抜け、出てきたチケットは作業量を少なく見積もっていました。ルーターが他のスキルについて述べたことをもとに行動するなら、先にその `SKILL.md` を開くよう頼んでください。地図がまったく扱っていない質問、たとえば [plan mode](https://www.aihero.dev/ai-coding-dictionary/agent-mode) を使うべきかどうかにも同じことが言えます: その答えは [model](https://www.aihero.dev/ai-coding-dictionary/model) の推測であって、ここに書かれていることではありません。

**なぜ番号付きのチェックリストではなく文章なのですか？**

もっともな不満です。ルーティングのほとんどは決定的で、文章だと流し読みしにくい、と主張する issue が開いています。短い形を求めるのは自由です: 「順序だけ教えて」と言えば順序が返ってきます。文章が担っているのは条件付きの部分です: 分岐、人間の判断が期待される場所、そしてステップの間でクリアや圧縮をする場所です。平らなチェックリストでは、まさにそこが抜け落ちます。

**自分のスキルや、他の作者のスキルにも案内してくれますか？**

いいえ。ローカルの `skills/` ディレクトリを読み、インストール済みのものから推奨するルーターを求める提案が 3 件別々にありました。`ask-matt` はそういうものではありません。手作業で保守される 1 つのセットの地図であり、あなたが書いたスキルや他所からインストールしたスキルについては何も知りません。

**SKILL.md を編集するように言われました。**

その助言は正しいことが多いのですが、編集が長続きすることはまれです。ある人が [implement](https://aihero.dev/skills-implement) にチケットを閉じさせるにはどうすればいいかを尋ね、スキルに 1 行足すよう言われて、すぐに問題に気づきました。`npx skills update` はファイルを上書きしますし、plugin のインストールは読み取り専用です。常に適用したい動作は自分の `CLAUDE.md` や `AGENTS.md` に書くか、呼び出すときに伝えてください。プロンプトで指定した変更は更新後も残ります。フローを GitHub ではなく Linear に向けたり、どの未完了チケットを並列に進められるかを尋ねたりするのも、この方法で行われています。

**持っていないスキルを挙げられた、または持っているスキルが抜けていました。**

なくなったと決めつける前に、changelog で名前の変更がないか確認してください。`writing-great-skills` は別名なしで [writing-for-agents](https://aihero.dev/skills-writing-for-agents) になり、`to-prd` は [to-spec](https://aihero.dev/skills-to-spec) に、`pathfinder` は [wayfinder](https://aihero.dev/skills-wayfinder) になりました。4 つのスキルは、それを吸収したスキルに統合されて完全に廃止されました: `ubiquitous-language`、`design-an-interface`、`qa`、`request-refactor-plan` です。持っているスキルが抜けているなら、それは上で説明したルーター自身の遅れです。

## 正常に機能している場合

- 最後に何を入力すべきかを示してそこで止まり、自分で作業を始めない。
- 返ってくるルートが、スキル名の一覧だけでなく、どこでコンテキストをクリアまたは圧縮するか、どこであなたのレビューが期待されるかに触れている。
- 2 つのスキルが近い場合に、どちらを使うべきか、そしてもう一方がなぜあなたに合わないかを述べている。
- 他のスキルの動作について述べたことが、そのスキルの `SKILL.md` を読んだ記録としてトレースに現れている。
- 返ってきた内容に、最も近い一般的なシナリオではなく、あなた自身の状況が反映されていると分かる。

## この機能の位置付け

`ask-matt` は、スキル全体の上に位置する**スタンドアロンのルーター**です。チェーンの 1 ステップになることは決してありません。すべてのチェーンへの入口を示し、他の docs ページもここにリンクを戻しているので、どのページもグラフを描き直す必要がありません。ここから最もよく行き着くのは、メインフローの先頭である [grill-with-docs](https://aihero.dev/skills-grill-with-docs) か、自分で始めた作業ではなく届いた作業のためのオンランプである [triage](https://aihero.dev/skills-triage) です。

これは、説明対象のスキルに対する [secondary source](https://www.aihero.dev/ai-coding-dictionary/secondary-source) です。ルーターと `SKILL.md` の内容が食い違う場合は、`SKILL.md` が正しいです。
