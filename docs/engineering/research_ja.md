## 機能

`research` は、答えを所有している情報源を読んで疑問に答え、引用付きの Markdown ファイルをリポジトリに残します。使うのは **[primary sources](https://www.aihero.dev/ai-coding-dictionary/primary-source)** だけです: 公式ドキュメント、ソースコード、仕様、ファーストパーティの API です。すべての主張をそれを所有する情報源までたどるので、API 自身のドキュメントにたどり着けるのに、ブログ記事による API の説明を繰り返すことはしません。

会話の中であなたに答えることはしません。成果物はファイルで、リポジトリがすでにそうしたメモを置いている場所に書かれ、各主張にリンクが付いています。[session](https://www.aihero.dev/ai-coding-dictionary/session) が終わると消えてしまう答えではなく、反応したり、別のエージェントに渡したり、捨てたりできる文書が手に入ります。

## この機能を使うタイミング

`/research` と入力するか、タスクが読み込みの手間仕事になったときに [agent](https://www.aihero.dev/ai-coding-dictionary/agent) が自動的に使います。

次のステップが、作業ディレクトリの外にある何かを*調べること*（サードパーティの API の挙動、仕様に書かれていること、あるバージョンについての主張が正しいかどうか）で、自分のスレッドを読み込みで止めたくないときに使います。必要なものによって、どのスキルかが決まります:

| 必要なもの | 使うもの |
| --- | --- |
| ある決定が待っている外部の事実 | `research` |
| インタビューによって、あなたと*一緒に*下す決定 | [grilling](https://aihero.dev/skills-grilling) |
| `GLOSSARY.md` と ADR に書き込まれる、長く残るアーキテクチャ上の決定 | [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| あるアプローチがあなたのコードベースで機能するかを確かめること | [prototype](https://aihero.dev/skills-prototype) |
| 1 セッションでは抱えきれない計画 | [wayfinder](https://aihero.dev/skills-wayfinder) |

`research` と `grill-with-docs` の分かれ目は、**返ってくるものの賞味期限**です。調査が生むのは短命な事実で、たとえば今週時点でこのライブラリの認証の仕組みが何をするか、といったものです。ADR は残しておく決定を記録します。生み出しているのが事実ではなく決定なら、あなたは調査ではなく [grilling](https://www.aihero.dev/ai-coding-dictionary/grilling) をしています。

## 委任された手間仕事

読み込みは**バックグラウンドエージェント**として実行されます。エージェントが各主張を一次情報までたどり、Markdown ファイルを 1 つ書いて報告する間、あなたは作業を続けられます。調査は委任する手間仕事であって、外注する思考ではありません。手に入るのは、グリル、計画、設計の材料にする文書であり、決定を下すのは今でもあなたです。

バックグラウンドエージェントが、さらに自分のバックグラウンドエージェントを起動するのを止めるものは何もありません。これはこのスキルで最もよく記録されている問題です。

ファイルをどこに置くかを決めるのは、スキルではなくリポジトリです。メモについてすでにある規約に従います。なければ妥当な場所を選び、それがどこかを伝えます。1 回の実行で書くファイルは 1 つです。

## よくある質問

**2 つ目の research エージェントが起動されました。これは想定どおりですか？**

いいえ。これは未解決のバグで、[issue #530](https://github.com/mattpocock/skills/issues/530) です。スキルは呼び出し側にバックグラウンドエージェントを起動するよう指示していますが、エージェントの種類を制限していません。そのため呼び出し側は `general-purpose` エージェントを起動し、そのエージェントは `Agent` ツールと同じ指示を持っているので、もう一度それに従ってしまいます。ある報告者は、1 つの調査タスクが、重複した 3 回の実行で約 45 万 [tokens](https://www.aihero.dev/ai-coding-dictionary/token) を消費したと計測しました。重複したほうは、ユーザーから見えない場所で 30 分後に終わっていました。Claude Code 以外でも起きます。ユーザーは GPT-5.6-sol を使った Codex でも同じ入れ子を確認しています。配布中の修正はありません。ユーザーは、すでに [subagent](https://www.aihero.dev/ai-coding-dictionary/subagent) であるエージェントには自分で作業させる、という 1 行をインストール済みのコピーに追加して対処しています。それは効果がありますが、あくまで指示であって、構造的な修正ではありません。スキルを呼び出した後は、バックグラウンドのタスク一覧を見て、重複したものを止めてください。

逆の失敗も起きます。あなた自身のグローバルな指示が、エージェントが作業を再委任することを禁じている場合、バックグラウンドエージェントはタスクを断り、スキルは何も知らせずに何もしません。

**ファイルはどこに置くべきですか？コミットすべきですか？**

スキルはリポジトリがすでにメモを置いている場所にファイルを置き、それ以上の意見は持っていません。コミュニティの見解はおおむね固まっています: 残すのは ADR で、調査ファイルではありません。この質問についてのある Discord のスレッドが最もはっきり述べています: 「ADR は残す。それ以外は、終わったらアーカイブするか削除する。そうしないと作業のゴミになり、spec や調査から離れてしまったときに、将来のリポジトリの読み込みを汚染しかねない。」調査ファイルは書かれた日に正しかったことを記録するものなので、古くなったものはないより悪いのです。総合すると、こうしたファイルは git に入れるべきではなく、決まった置き場所もありません。代わりに Obsidian、別の知識用リポジトリ、issue tracker などが使われています。

**何が「信頼性の高い」一次情報に当たり、それを誰が決めるのですか？**

決めるのは [model](https://www.aihero.dev/ai-coding-dictionary/model) です。スキルは該当する情報源の*種類*（公式ドキュメント、ソースコード、仕様、ファーストパーティの API）を挙げていますが、許可リストも、ドメインの制限も、検証の工程もありません。これはスキルが最初に提案されたときに最も大きく上がった異議で、公には誰も答えていません: 「ゴミに向けた 5 つの research サブエージェントは、自信たっぷりの間違った答えを 5 つ、より速く返すだけだ。何を信頼性の高い情報源とみなすか、どうやって制限しているのか？」あなたを守るものは、各主張に付いた引用だけです。そのうち 2〜3 個をたどってみてください。それが物そのものではなく、物の要約にたどり着くなら、その実行は失敗です。

**後のセッションは、以前の実行で見つけたことを再利用しますか？**

いいえ。過去の調査ファイルを自動で読み込むものは何もありません。人間かスキルがそれを指すまで、ファイルはリポジトリに置かれたままです。これは設計に対する初期の最も強い疑問でした: 「価値があるのは取得そのものではなく、Markdown がエージェントが後で読み直すコンテキストになることだ。一度書いて放置されるファイルは、ただの凝った検索にすぎない。」配布中のスキルはこれを解決していません。実際には、ファイルが役に立つのは、次のステップにあなた自身がそれを渡したときだけです: spec に添付する、グリルのセッションに引用する、[ticket](https://www.aihero.dev/ai-coding-dictionary/ticket) からそれを指す、などです。

**エージェントにドキュメントを読んでくるよう頼むだけではだめなのですか？**

それもできますし、まさにそう言う 2 行のプロンプトが、このスキルが置き換えたやり方でした。このスキルは、そのプロンプトにはない 2 つのものを与えてくれます。バックグラウンドで実行されるので、セッションの [context](https://www.aihero.dev/ai-coding-dictionary/context) がきれいなまま保たれます。そして、一次情報という制約と引用付きファイルという出力が、プロンプトの言い回しに左右されずに毎回同じになります。[harness](https://www.aihero.dev/ai-coding-dictionary/harness) 自身のディープリサーチのモードと比べると、違いは検索ではなく、ファイルと一次情報のルールです。小さな疑問で 2 行のプロンプトで十分なら、2 行のプロンプトを使ってください。

**いつ読むのをやめるのですか？**

スキルには停止条件がありません。これは、正反対に見えて原因が同じ 2 つの不満として現れます: 深く掘りすぎるエージェントと、テーマを広くカバーしながら肝心の 1 つの詳細を見逃すエージェントです。ある実践者はこう表現しました: 「ディープリサーチ系のスキルは、ときどき少し深すぎる。そしてエージェントに調査を頼むと、たいてい決定的な詳細を見逃す。」範囲はあなたが決める必要があります。狭く、答えられる疑問（1 つの API、1 つの振る舞い、1 つのバージョンについての主張）のほうが、「X を調べて」よりずっと良い結果が返ってきます。

**`/wayfinder` が research チケットを作りました。それは自分で解決するのですか？**

いいえ、今は wayfinder が代わりに実行してくれます。v1.1 以降の未リリースの変更では、マップを描くセッションが research チケットごとに `/research` のサブエージェントを 1 つ起動し、並列に実行します。それぞれは結果を使い捨ての `research/<name>` ブランチに記録し、チケットからそこへの [context pointer](https://www.aihero.dev/ai-coding-dictionary/context-pointer) を置きます。research チケットは、wayfinder の 1 セッション 1 チケットというルールの唯一の例外です。[AFK](https://www.aihero.dev/ai-coding-dictionary/afk) なので、あなたを待つものが何もないからです。既知の問題が 1 つあります: 後でブランチを削除すると、チケット内の context pointer が壊れます。

## 正常に機能している場合

- あなた自身のセッションが進み続ける。座って読み込みを眺めているなら、委任は起きていません。
- 新しいバックグラウンドタスクがちょうど 1 つだけ現れる。ほぼ同じ名前の 2 つ目があれば、それは入れ子のバグです。
- リポジトリがすでにメモに使っているフォルダに新しい Markdown ファイルが 1 つ現れ、エージェントがそのパスを伝える。
- その中のすべての主張にリンクが付いていて、適当に 2 つたどると、誰かの解説ではなく、公式ドキュメント、仕様、またはソースファイルそのものにたどり着く。
- 自分で情報源に戻らなくても、そのファイルだけで、行き詰まっていた決定を下せる。

## この機能の位置付け

`research` はいつでも使えるスタンドアロンです。思考系のスキルに材料を与えるもので、ビルドチェーンのステップではありません。そのファイルをフローに*持ち込む*のはあなたです。[grilling](https://aihero.dev/skills-grilling) と [grill-with-docs](https://aihero.dev/skills-grill-with-docs) は、事実がすでにあるとより鋭い質問をし、[to-spec](https://aihero.dev/skills-to-spec) はそれを踏まえてまとめることができます。これを直接呼び出す唯一のスキルが [wayfinder](https://aihero.dev/skills-wayfinder) で、マップ上の各 research チケットを `/research` のサブエージェントで解決します。全体の地図は [ask-matt](https://aihero.dev/skills-ask-matt) を参照してください。
